# 2. 短剧微服务架构文档

## 微服务架构概述

基于业务领域和功能模块，我们将短剧App拆分为以下微服务：

1. **用户服务(User Service)**：负责用户注册、登录、认证、个人信息管理
2. **内容服务(Content Service)**：负责短剧和剧集的管理
3. **互动服务(Interaction Service)**：负责评论、点赞、分享等社交互动功能
4. **播放服务(Playback Service)**：负责播放历史、追剧等功能
5. **搜索服务(Search Service)**：负责搜索功能和热搜榜
6. **活动服务(Activity Service)**：负责签到、福利活动等运营活动
7. **支付服务(Payment Service)**：负责金币、现金交易和VIP会员管理
8. **消息服务(Message Service)**：负责系统消息和通知
9. **广告服务(Advertisement Service)**：负责广告投放和管理

## 数据库拆分策略

每个微服务拥有自己独立的数据库，服务间通过API调用或消息队列进行通信。数据库拆分遵循以下原则：

1. **高内聚**：相关性强的数据放在同一个数据库中
2. **低耦合**：减少跨数据库的关联查询
3. **数据冗余**：适当冗余关键数据，减少跨服务查询
4. **最终一致性**：通过事件驱动确保分布式数据的最终一致性

## 微服务数据库设计

### 用户服务数据库(user_service_db)

```sql
CREATE DATABASE IF NOT EXISTS user_service_db DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

USE user_service_db;

-- 用户表
CREATE TABLE users (
  user_id bigint(20) NOT NULL AUTO_INCREMENT COMMENT '用户ID',
  phone varchar(20) DEFAULT NULL COMMENT '手机号',
  wechat_openid varchar(64) DEFAULT NULL COMMENT '微信OpenID',
  nickname varchar(50) DEFAULT NULL COMMENT '昵称',
  avatar varchar(255) DEFAULT NULL COMMENT '头像URL',
  gender tinyint(1) DEFAULT 0 COMMENT '性别：0未知，1男，2女',
  birthday date DEFAULT NULL COMMENT '生日',
  register_time datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '注册时间',
  last_login_time datetime DEFAULT NULL COMMENT '最后登录时间',
  status tinyint(1) NOT NULL DEFAULT 1 COMMENT '状态：0禁用，1正常',
  PRIMARY KEY (user_id),
  UNIQUE KEY idx_phone (phone),
  UNIQUE KEY idx_wechat_openid (wechat_openid)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';

-- 用户偏好表
CREATE TABLE user_preferences (
  preference_id bigint(20) NOT NULL AUTO_INCREMENT COMMENT '偏好ID',
  user_id bigint(20) NOT NULL COMMENT '用户ID',
  category_id bigint(20) NOT NULL COMMENT '分类ID',
  create_time datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  PRIMARY KEY (preference_id),
  KEY idx_user_id (user_id),
  KEY idx_category_id (category_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户偏好表';

-- 用户设备表
CREATE TABLE user_devices (
  device_id bigint(20) NOT NULL AUTO_INCREMENT COMMENT '设备ID',
  user_id bigint(20) NOT NULL COMMENT '用户ID',
  device_type varchar(20) NOT NULL COMMENT '设备类型：iOS/Android',
  device_token varchar(255) DEFAULT NULL COMMENT '设备推送令牌',
  app_version varchar(20) DEFAULT NULL COMMENT 'App版本',
  last_active_time datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '最后活跃时间',
  PRIMARY KEY (device_id),
  KEY idx_user_id (user_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户设备表';

-- 用户认证表
CREATE TABLE user_auths (
  auth_id bigint(20) NOT NULL AUTO_INCREMENT COMMENT '认证ID',
  user_id bigint(20) NOT NULL COMMENT '用户ID',
  auth_type varchar(20) NOT NULL COMMENT '认证类型：password/sms/wechat',
  auth_key varchar(64) NOT NULL COMMENT '认证标识',
  auth_credential varchar(255) NOT NULL COMMENT '认证凭证',
  create_time datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  update_time datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (auth_id),
  UNIQUE KEY idx_auth_type_key (auth_type, auth_key),
  KEY idx_user_id (user_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户认证表';
```

  create_time datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  update_time datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',

  UNIQUE KEY idx_drama_episode (drama_id, episode_number),
  KEY idx_drama_id (drama_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='剧集表';

-- 标签表
CREATE TABLE tags (
  tag_id bigint(20) NOT NULL AUTO_INCREMENT COMMENT '标签ID',

  UNIQUE KEY idx_drama_tag (drama_id, tag_id),

## 微服务间数据同步与一致性

在微服务架构中，数据一致性是一个重要挑战。我们采用以下策略来确保数据一致性：

## 事件驱动架构

使用消息队列（如Kafka、RabbitMQ）实现服务间的事件通知，确保数据变更能够在各个服务间同步。

主要事件类型：

- 用户注册/更新事件
- 内容发布/更新事件
- 订单状态变更事件
- 播放记录事件
- 互动行为事件（评论、点赞等）

## 数据冗余策略

在某些微服务中适当冗余其他服务的关键数据，减少跨服务查询。例如：

- 播放服务中冗余了短剧和剧集的基本信息
- 活动服务中冗余了短剧的基本信息
- 互动服务中冗余了用户的基本信息

## 分布式事务

对于关键业务流程（如支付），采用最终一致性的分布式事务模式：

- Saga模式
- TCC（Try-Confirm-Cancel）模式
- 本地消息表模式

## 数据版本控制

使用版本号或时间戳来跟踪数据变更，解决并发更新冲突。

## 微服务API网关设计

API网关作为客户端与微服务之间的中间层，负责请求路由、组合、协议转换等功能。

主要功能：

- **路由转发**：将请求路由到相应的微服务
- **身份认证**：统一的用户认证和授权
- **限流熔断**：防止服务过载
- **请求聚合**：组合多个服务的数据，减少客户端请求次数
- **日志监控**：记录请求日志，监控服务性能

## 微服务部署与扩展

每个微服务可以独立部署和扩展，根据业务需求和负载情况进行水平扩展。

部署策略：

- 容器化部署（Docker + Kubernetes）
- 服务注册与发现（Nacos）
- 配置中心（Nacos）
- 负载均衡（Nginx、LoadBalancer）
- 远程调用（OpenFeign）

## 数据库扩展策略

随着业务增长，可以采用以下策略进行数据库扩展：

1. **读写分离**：主库负责写操作，从库负责读操作
2. **分库分表**：
  - 水平分片：按用户ID或时间范围分片
  - 垂直分片：按业务功能拆分表
3. **缓存策略**：使用Redis缓存热点数据
4. **数据归档**：定期将历史数据归档到冷存储

## 安全性考虑

1. **服务间通信安全**：
  - 服务间通信使用HTTPS或内部加密通道
  - 服务间认证使用JWT或OAuth2.0
2. **数据安全**：
  - 敏感数据加密存储
  - 数据访问权限控制
  - 定期数据备份
3. **API安全**：
  - 接口限流
  - 防SQL注入
  - 防XSS攻击

## 监控与日志

1. **集中式日志系统**：
  - ELK栈（Elasticsearch, Logstash, Kibana）
  - 日志聚合与分析
2. **监控系统**：
  - Prometheus + Grafana
  - 服务健康检查
  - 性能指标监控

## 结论

基于微服务架构的短剧App数据库设计，将系统拆分为9个核心微服务，每个微服务拥有自己独立的数据库。这种设计具有以下优势：

1. **高内聚低耦合**：每个微服务专注于特定业务领域
2. **独立部署与扩展**：各服务可以根据负载情况独立扩展
3. **技术栈灵活性**：不同微服务可以使用最适合的技术栈
4. **故障隔离**：单个服务故障不会影响整个系统
5. **团队自治**：不同团队可以独立负责不同的微服务

同时，我们也需要面对微服务架构带来的挑战，如数据一致性、分布式事务、服务治理等问题，并通过合理的技术方案来解决这些问题。
