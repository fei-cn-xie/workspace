# 1. AI 生态面试题大全

### 说说 NumPy 的 broadcasting 机制是怎么回事？

**答： **简单说就是 NumPy 在做数组运算时，如果两个数组形状不一样，它会自动把小的那个"广播"成大的形状。规则是从最后一个维度开始对齐，维度为 1 的可以扩展，维度不存在的可以补 1。

比如一个 (3,4) 的矩阵加一个 (4,) 的向量，向量会被广播成 (3,4)，每一行都加上这个向量。

### Pandas 里 apply 和 vectorized 操作性能差多少？什么时候该用哪个？

**答： **差距很大，通常 vectorized 操作比 apply 快 10-100 倍。apply 本质是 Python 层面的循环，而 vectorized 操作走的是底层 C/Fortran。

能用内置方法（如 `df['col'].str.contains()` 、 `df['col'] * 2` ）就别用 apply。只有逻辑特别复杂、没法向量化的时候才用 apply，而且这时候可以考虑用 `numba` 加速。

### FastAPI 的依赖注入是怎么工作的？跟 Spring 的 DI 有什么区别？

**答： **FastAPI 的依赖注入是基于函数参数的。你在路由函数的参数里声明 `Depends(some_function)` ，框架会自动调用这个函数并把返回值注入进来。它支持嵌套依赖、yield 依赖（类似上下文管理器）。

跟 Spring 的区别是：Spring 是基于类和容器的 IoC，生命周期管理更重；FastAPI 是轻量级的、基于函数调用链的，每次请求重新执行依赖函数（除非你自己做缓存）。

### SQLAlchemy 2.0 相比 1.x 最大的变化是什么？

**答： **最大变化是统一了查询风格。2.0 废弃了 `session.query()` 那套老 API，全面转向 `select()` 语句式写法。执行也从 `session.query(User).filter(...)` 变成了 `session.execute(select(User).where(...))` 。

另外 2.0 默认开启了"future"模式，连接和事务管理更显式，不再有隐式 autocommit。类型提示支持也好了很多，配合 `Mapped[]` 注解写 ORM 模型更清晰。

### OpenAI SDK 的 Chat Completions 接口，messages 里 system、user、assistant 三种 role 分别起什么作用？

**答：**

- **system **：设定模型的行为边界和人设，优先级最高，模型会尽量遵守
- **user **：用户的输入，就是你要问的问题或指令
- **assistant **：模型之前的回复，用来维持多轮对话上下文

实际使用中，system message 放在最前面，然后 user/assistant 交替排列形成对话历史。few-shot 示例也是通过 user/assistant 对来实现的。

### matplotlib 画图时 figure 和 axes 是什么关系？

**答： **figure 是整个画布，axes 是画布上的一个子图区域。一个 figure 可以包含多个 axes。

推荐用法是 `fig, ax = plt.subplots()` ，这样你拿到的 ax 对象可以精确控制每个子图。别用 `plt.plot()` 这种隐式接口，多图的时候容易乱。

### Conda 虚拟环境和 venv 有什么本质区别？

**答： **最大区别是 conda 能管理非 Python 的依赖（比如 CUDA、cuDNN、C 库），venv 只管 Python 包。conda 有自己的包解析器，能处理跨语言依赖冲突。

做深度学习项目基本都用 conda，因为 GPU 驱动和 CUDA 版本匹配很头疼，conda 能帮你搞定。纯 Web 开发用 venv + pip 就够了，更轻量。

### Coze 和 Dify 这类平台的核心价值是什么？什么场景下你会选择用它们而不是自己写代码？

**答： **核心价值是低代码快速搭建 AI 应用，特别适合：

- 快速验证想法/做 MVP
- 非技术团队需要用 AI 能力
- 简单的工作流编排（比如客服机器人、知识库问答）

但如果你需要深度定制、复杂的状态管理、或者对延迟和成本有严格要求，还是得自己写代码。这些平台的灵活性和可调试性都有限。

### ComfyUI 的节点式工作流相比代码调用 Stable Diffusion 有什么优势？

**答： **优势主要是可视化和可复现。你能直观看到整个生成管线：从加载模型、设置采样器、到后处理，每一步的输入输出都清清楚楚。工作流可以保存为 JSON 分享给别人。

对于需要反复调参、对比不同 ControlNet/LoRA 组合效果的场景特别好用。但如果是批量生产或者要集成到后端服务里，还是得用代码调 API。

### 用 OpenAI SDK 做流式输出（streaming）时，怎么处理？

**答： **用 `stream=True` 参数，然后迭代返回的 response：

```python
from openai import OpenAI
client = OpenAI()

stream = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "你好"}],
    stream=True
)

for chunk in stream:
    if chunk.choices[0].delta.content is not None:
        print(chunk.choices[0].delta.content, end="")
```

每个 chunk 里的 `delta.content` 是增量文本。注意第一个和最后一个 chunk 可能 content 为 None，要做判断。

### Claude Code 是什么？跟 Cursor、GitHub Copilot 有什么区别？

**答： **Claude Code 是 Anthropic 出的 CLI 工具，直接在终端里跟 Claude 交互，它能读写你的文件、执行 shell 命令、操作 git。本质上是一个有完整系统访问权限的 AI 编程 Agent。

跟其他工具的区别：

| 工具 | 形态 | 特点 |
| --- | --- | --- |
| Claude Code | CLI / IDE 插件 | 终端原生，能直接操作文件系统和 git，Agent 模式 |
| Cursor | IDE（VS Code fork） | 编辑器深度集成，Tab 补全 + Chat + Composer |
| GitHub Copilot | IDE 插件 | 行级/块级补全为主，Chat 为辅 |
| Windsurf | IDE（VS Code fork） | 类似 Cursor，强调 Flow 模式 |

Claude Code 的优势是不绑定 IDE，适合习惯终端工作流的开发者，而且它的 Agent 能力很强——你可以让它自己去读代码、跑测试、修 bug，整个流程自动化。

### Claude Code 日常怎么用？有哪些高效用法？

**答： **几个核心用法：

1. **代码理解 **：进入项目目录，直接问"这个项目的架构是什么？入口在哪？"，它会自己读文件、分析代码
2. **写功能 **：描述需求，它会自己找到该改的文件、写代码、跑测试
3. **修 bug **：贴上报错信息，它会自己定位问题、修复、验证
4. **Git 操作 **：让它帮你写 commit message、创建 PR、review 代码
5. **重构 **：比如"把这个模块从 class 改成函数式"，它会批量修改

高效技巧：

- 项目根目录放一个 `CLAUDE.md` ，写上项目背景、技术栈、代码规范，Claude Code 每次启动会自动读
- 用 `/init` 命令自动生成 CLAUDE.md
- 复杂任务让它先出计划再执行，别一上来就让它改代码
- 善用 `!` 前缀在对话中直接跑 shell 命令

### CLAUDE.md 是什么？怎么写才有效？

**答： **CLAUDE.md 是 Claude Code 的项目级上下文文件，放在项目根目录。每次启动 Claude Code 时自动加载，相当于给 AI 一个项目说明书。

有效的 CLAUDE.md 应该包含：

```plaintext
# 项目概述
这是一个基于 FastAPI + React 的知识库问答系统。

# 技术栈
- 后端: FastAPI + SQLAlchemy 2.0 + Milvus
- 前端: React 18 + TypeScript + Tailwind
- 部署: Docker + K8s

# 代码规范
- Python 用 ruff 格式化，行宽 120
- 函数命名用 snake_case
- 提交信息用中文

# 常用命令
- 启动开发: make dev
- 跑测试: make test
- 类型检查: make typecheck

# 架构要点
- API 路由在 src/api/ 下
- 业务逻辑在 src/services/ 下
- 不要直接在路由里写业务逻辑
```

关键是写那些 AI 从代码里不容易推断出来的信息：团队约定、架构决策的原因、踩过的坑。

### AI 辅助编程的工作流是什么样的？你日常怎么用？

**答： **我的典型工作流：

```plaintext
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│ 需求理解  │───→│ AI 写初稿 │───→│ 人工审查  │───→│ AI 迭代   │
│(人主导)   │    │(AI主导)   │    │(人主导)   │    │(协作)     │
└──────────┘    └──────────┘    └──────────┘    └──────────┘
```

具体来说：

1. **需求阶段 **：我先想清楚要做什么，必要时让 AI 帮我梳理技术方案
2. **编码阶段 **：简单代码让 Copilot 补全；复杂功能用 Claude Code 或 Cursor 的 Agent 模式
3. **Review 阶段 **：AI 写的代码一定要看，重点看边界条件、安全问题、是否过度设计
4. **调试阶段 **：报错直接丢给 AI，它定位问题比我翻文档快

核心原则：AI 是加速器不是替代品。你得知道它写的对不对，不能盲信。

### Cursor 的 Agent 模式和 Tab 补全模式分别适合什么场景？

**答：**

**Tab 补全 **：写代码时实时补全下一行或下一块

- 适合：日常编码、写重复性代码、补全函数体
- 特点：快、无打断、上下文是当前文件

**Agent 模式（Composer） **：给一个需求，AI 自动跨文件修改

- 适合：新功能开发、重构、跨文件修改
- 特点：能读写多个文件、跑命令、自动迭代

**Chat 模式 **：问答式交互

- 适合：理解代码、讨论方案、学习新技术

```plaintext
写一行代码 → Tab 补全
改一个文件 → Chat
改多个文件 → Agent/Composer
```

经验：别什么都用 Agent 模式，简单的事情 Tab 补全更快。

Agent 模式适合那种你描述清楚需求后，需要改 3-5 个文件的任务。

### AI 代码生成的质量怎么保证？有哪些常见坑？

**答： **常见坑：

1. **幻觉 API **：AI 编造不存在的库或方法，特别是新框架
2. **过度设计 **：简单需求写出一堆抽象层和设计模式
3. **安全漏洞 **：SQL 注入、XSS、硬编码密钥
4. **过时写法 **：用了废弃的 API（比如 LangChain 的 LCEL）
5. **忽略边界条件 **：空值、并发、大数据量

保证质量的做法：

- **必须 code review **：AI 写的代码跟人写的一样需要审查
- **跑测试 **：让 AI 同时写单元测试
- **类型检查 **：TypeScript / mypy 能抓住很多问题
- **给上下文 **：告诉 AI 用什么版本的库、遵循什么规范
- **小步迭代 **：别一次让 AI 写 500 行，分成小任务

### GitHub Copilot Workspace 和传统 Copilot 有什么区别？

**答： **传统 Copilot 是编辑器里的补全工具，Workspace 是一个完整的 AI 开发环境：

```plaintext
传统 Copilot:  你写代码 → AI 补全下一行
Workspace:     你描述需求 → AI 出方案 → AI 写代码 → AI 开 PR
```

Workspace 的流程：

1. 从 GitHub Issue 出发
2. AI 分析 issue，生成实现计划
3. AI 根据计划修改代码
4. 你审查、调整
5. 直接创建 PR

本质上是把 Copilot 从"代码补全"升级到了"任务完成"。跟 Claude Code 的 Agent 模式类似，但更深度集成 GitHub 生态。

### AI 怎么融入代码 Review 流程？

**答： **几种方式：

1. **PR Review Bot **：GitHub 上配置 AI review bot（如 CodeRabbit、Claude Code 的 `/review` ），自动对 PR 做初审
2. **安全扫描 **：AI 检查常见安全漏洞
3. **辅助人工 Review **：reviewer 用 AI 快速理解大 PR 的改动意图

```plaintext
PR 提交
  │
  ├→ AI Bot 自动 Review (格式、安全、常见问题)
  │
  ├→ CI/CD 跑测试
  │
  └→ 人工 Review (架构、业务逻辑、设计决策)
       └→ 遇到不确定的地方，问 AI 解释
```

注意：AI Review 是辅助不是替代。它擅长抓格式问题、潜在 bug、安全漏洞，但架构决策和业务逻辑还是得人来判断。

### Prompt Engineering 在日常开发中有哪些实用技巧？

**答： **跟 AI 编程工具交互的 prompt 技巧：

1. **给上下文 **：不要说"写一个函数"，要说"在 src/services/user.py 中，用 SQLAlchemy 2.0 写一个查询用户的函数，返回 Pydantic model"
2. **给约束 **：明确技术栈版本、代码风格、不要用什么
3. **给示例 **：贴一个现有的类似函数，说"参考这个风格"
4. **分步骤 **：复杂任务拆成小步，每步确认后再继续
5. **让它解释 **：不确定的代码让 AI 解释为什么这么写

反模式：

- "帮我写个网站" → 太模糊
- 一次性丢 2000 行代码让它重构 → 太大
- 不给任何上下文就问"这个 bug 怎么修" → 缺信息

### AI 辅助写测试有哪些好的实践？

**答： **AI 写测试其实比写业务代码更靠谱，因为测试的模式更固定。

好的做法：

1. **先写业务代码，再让 AI 生成测试 **：给它看实现代码，让它生成覆盖各种 case 的测试
2. **指定测试框架 **：明确说"用 pytest + pytest-asyncio"，别让它自己选
3. **要求覆盖边界条件 **：明确说"包含空值、异常、并发场景的测试"
4. **让 AI 生成测试数据 **：造 mock 数据是 AI 的强项

提示词示例：

```plaintext
提示词示例：
"为 src/services/order.py 中的 create_order 函数写 pytest 测试。
覆盖：正常创建、库存不足、用户不存在、并发下单。
用 pytest fixture 管理测试数据，mock 外部支付接口。"
```

注意：AI 生成的测试要跑一遍确认能过。有时候它会写出逻辑上正确但实际跑不通的测试（比如 mock 路径写错）。

### MCP（Model Context Protocol）是什么？为什么重要？

**答： **MCP 是 Anthropic 提出的协议，让 AI 模型能标准化地连接外部工具和数据源。

```plaintext
没有 MCP:
每个 AI 工具 × 每个数据源 = N×M 种集成方式

有了 MCP:
AI 工具 → MCP 协议 → MCP Server → 数据源
                      (标准接口)
```

类比：MCP 之于 AI 工具，就像 USB 之于外设。不管什么 AI 工具（Claude Code、Cursor、Cline），只要支持 MCP，就能连接任何 MCP Server（数据库、Jira、Slack、文件系统...）。

为什么重要：

- AI Agent 需要访问外部系统才能真正有用
- 没有标准协议，每个工具都要自己写集成，生态碎片化
- MCP 让工具开发者和数据源提供者各做各的，通过协议对接

Claude Code 原生支持 MCP，可以在配置里添加 MCP Server。

### AI 编程工具的 Context 管理为什么重要？怎么优化？

**答： **Context 就是你喂给 AI 的上下文信息。Context 质量直接决定 AI 输出质量。

问题：模型的 context window 有限（4K-200K tokens），你的项目可能有几十万行代码，不可能全塞进去。

优化策略：

```plaintext
┌─────────────────────────────────────┐
│         Context 优先级               │
├─────────────────────────────────────┤
│ 1. 当前正在编辑的文件    (必须)      │
│ 2. 直接相关的文件        (重要)      │
│ 3. 类型定义/接口         (有用)      │
│ 4. 项目配置/规范         (背景)      │
│ 5. 其他文件              (按需)      │
└─────────────────────────────────────┘
```

实操：

- **CLAUDE.md / .cursorrules **：把项目规范写进去，自动加载
- **手动 @文件 **：在 Cursor/Claude Code 中手动引用相关文件
- **让 AI 自己找 **：Claude Code 的 Agent 模式会自己搜索相关代码
- **精简 prompt **：别贴无关代码，噪声会降低质量

### 未来 AI 辅助开发会发展成什么样？开发者该怎么准备？

**答： **趋势判断：

```plaintext
以前:     AI 补全代码 → 人写大部分，AI 辅助
现在:  AI Agent 写代码 → 人描述需求+审查，AI 执行
1-3年后:  AI 自主开发 → 人定义目标+验收，AI 全流程
3-5年后： AI 开发 -> 验收 -> 上线 全自动；就像流浪地球MOSS给每个行星发动机现场编写操作系统一样

未来你需要什么功能软件，AI现场帮你写，帮你做
```

但这不意味着开发者会失业。变化的是工作内容：

- **减少 **：写 boilerplate、查文档、调格式、写简单 CRUD
- **增加 **：需求分析、架构设计、AI 输出审查、系统集成、领域知识

开发者该准备什么：

1. **学会跟 AI 协作 **：prompt engineering 是基本功
2. **强化系统设计能力 **：AI 能写函数但不擅长设计系统
3. **深耕领域知识 **：医疗、金融、法律等领域知识 AI 替代不了
4. **理解 AI 原理 **：知道 AI 能做什么、不能做什么、什么时候会出错
5. **保持学习 **：工具在快速迭代，半年前的最佳实践可能已经过时

最重要的一条：不要抗拒 AI，也不要盲信 AI。把它当成一个很强但偶尔犯蠢的搭档。
