# 4. 模型微调 面试题大全

## 模型微调

### 什么是 LoRA？为什么现在微调基本都用它？

**答： **LoRA（Low-Rank Adaptation）的核心思想是：大模型的权重更新矩阵是低秩的，不需要更新全部参数。

```plaintext
原始权重 W (d×d)          LoRA 分解
┌─────────────┐          ┌───┐   ┌─────────────┐
│             │          │   │   │             │
│   W (冻结)   │    +     │ A │ × │      B      │
│             │          │   │   │             │
│  d × d      │          │d×r│   │   r × d     │
└─────────────┘          └───┘   └─────────────┘
                          r << d (如 r=8,16,64)
```

参数量从 d² 降到 2dr，比如 d=4096, r=16，参数量从 1600万 降到 13万，减少了 99%。

为什么都用它：

- 训练显存大幅降低（只需存储小矩阵的梯度）
- 训练速度快
- 可以为不同任务训练不同 LoRA，推理时热切换
- 效果接近全量微调

### QLoRA 比 LoRA 又多了什么？

**答： **QLoRA = 量化基础模型 + LoRA 微调。三个关键创新：

1. **4-bit NormalFloat 量化 **：把基础模型量化到 4bit，大幅减少显存
2. **双重量化 **：对量化常数再做一次量化
3. **分页优化器 **：用 CPU 内存处理 GPU 显存溢出

效果：一张 24GB 的 4090 就能微调 65B 参数的模型。而且效果跟 16bit LoRA 几乎一样。

全量微调 70B: 需要 ~140GB 显存 (多卡A100)

LoRA 微调 70B: 需要 ~80GB 显存

QLoRA 微调 70B: 需要 ~24GB 显存 (单卡就行!)

### 微调数据怎么准备？格式是什么样的？

**答： **最常见的是指令微调（Instruction Tuning）格式：

```json
{"messages": [
    {"role": "system", "content": "你是一个专业的法律顾问"},
    {"role": "user", "content": "租房合同到期房东不退押金怎么办？"},
    {"role": "assistant", "content": "根据《民法典》第七百一十四条..."}
]}
```

数据质量 > 数据数量。几百条高质量数据的效果可能比几万条低质量数据好。

准备建议：

- 多样性：覆盖你想要的各种场景
- 一致性：同类问题的回答风格要统一
- 长度适中：太短学不到东西，太长容易过拟合
- 去重：重复数据会导致模型记忆而非泛化

### 全量微调、LoRA、Prompt Tuning 怎么选？

**答：**

| 方法 | 参数量 | 显存需求 | 效果 | 适用场景 |
| --- | --- | --- | --- | --- |
| 全量微调 | 1 | 极高 | 最好 | 有充足算力，任务差异大 |
| LoRA | 0.1-1% | 低 | 接近全量 | 大多数场景首选 |
| QLoRA | 0.1-1% | 极低 | 略低于LoRA | 显存有限 |
| Prompt Tuning | <0.01% | 最低 | 一般 | 简单分类任务 |

实际项目中 90% 的情况用 LoRA/QLoRA 就够了。只有当你的任务跟预训练数据差异特别大（比如训练一个全新语言），才需要全量微调。

### 微调时的超参数怎么调？哪些最关键？

**答： **最关键的几个：

1. **Learning Rate **：LoRA 一般 1e-4 到 2e-4，全量微调 1e-5 到 5e-5。太大会崩，太小收敛慢
2. **LoRA Rank (r) **：8-64 之间，任务越复杂 rank 越大。一般从 16 开始试
3. **Epochs **：指令微调通常 3-5 个 epoch 就够，多了容易过拟合
4. **Batch Size **：越大越稳定，但受显存限制。用 gradient accumulation 模拟大 batch
5. **LoRA Alpha **：通常设为 rank 的 2 倍（alpha=32 when r=16）

调参策略：先用小数据集快速试几组参数，找到大致范围，再用全量数据训练。

### 什么是 DPO？跟 RLHF 有什么区别？

**答：**

RLHF（Reinforcement Learning from Human Feedback，基于人类反馈的强化学习）流程：

```plaintext
SFT模型 → 训练奖励模型(RM) → PPO强化学习优化
```

DPO（Direct Preference Optimization）直接偏好优化 流程：

```plaintext
SFT模型 → 直接用偏好数据优化（不需要RM）
```

DPO 把 RLHF 的目标函数做了数学变换，证明可以直接从偏好对数据中学习，不需要单独训练奖励模型。

数据格式：

```json
{
    "prompt": "解释量子计算",
    "chosen": "量子计算利用量子力学原理...(好的回答)",
    "rejected": "量子计算就是很快的计算机...(差的回答)"
}
```

DPO 优势：实现简单、训练稳定、不需要额外的 RM。现在大部分对齐训练都用 DPO 或其变体。

### 微调后模型效果变差了（灾难性遗忘），怎么办？

**答： **灾难性遗忘是微调的经典问题，几个解决方案：

1. **降低学习率 **：用更小的 lr，让模型温和地适应新任务
2. **混合训练数据 **：在微调数据中混入一部分通用数据（比如 10-20%）
3. **LoRA 而非全量微调 **：LoRA 天然缓解遗忘，因为原始权重冻结了
4. **正则化 **：L2 正则或 weight decay 防止参数偏移太远
5. **评估多维度 **：不只看目标任务指标，也要监控通用能力（用 benchmark 跑分）

最实用的是第 2 条，混合数据。比如你在做医疗问答微调，混入 10% 的通用对话数据，能有效保持模型的通用能力。

### 用 Hugging Face Transformers + PEFT 做 LoRA 微调的代码流程是什么？

```plaintext
from transformers import AutoModelForCausalLM, AutoTokenizer, TrainingArguments
from peft import LoraConfig, get_peft_model, TaskType
from trl import SFTTrainer

# 1. 加载基础模型
model = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen2.5-7B-Instruct",
    torch_dtype=torch.bfloat16,
    device_map="auto"
)
tokenizer = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-7B-Instruct")

# 2. 配置 LoRA
lora_config = LoraConfig(
    task_type=TaskType.CAUSAL_LM,
    r=16,
    lora_alpha=32,
    lora_dropout=0.05,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj"]
)
model = get_peft_model(model, lora_config)

# 3. 训练
trainer = SFTTrainer(
    model=model,
    train_dataset=dataset,
    args=TrainingArguments(
        output_dir="./output",
        num_train_epochs=3,
        per_device_train_batch_size=4,
        learning_rate=2e-4,
        bf16=True,
    ),
)
trainer.train()

# 4. 保存 LoRA 权重
model.save_pretrained("./lora_weights")
```

### target_modules 怎么选？为什么一般选 attention 层？

**答： **`target_modules` 决定了 LoRA 应用在模型的哪些层。

常见选择：

- **最小集 **： `["q_proj", "v_proj"]` — 原始 LoRA 论文的推荐
- **推荐集 **： `["q_proj", "k_proj", "v_proj", "o_proj"]` — attention 全覆盖
- **最大集 **：再加上 `["gate_proj", "up_proj", "down_proj"]` — 包含 FFN 层

为什么选 attention 层？因为 attention 是模型学习"关注什么"的核心机制，微调它能最有效地改变模型行为。FFN 层更多是存储知识，如果你的任务需要注入新知识（而非改变行为），可以加上 FFN。

实践中用 attention 全覆盖（q/k/v/o）是性价比最高的选择。

### 什么是 SFT（Supervised Fine-Tuning）？它在整个训练流程中处于什么位置？

**答： **大模型训练的完整流程：

```plaintext
┌──────────┐    ┌──────────┐    ┌──────────┐
│ 预训练    │───→│   SFT    │───→│  对齐     │
│(Pre-train)│    │(指令微调) │    │(DPO/RLHF)│
└──────────┘    └──────────┘    └──────────┘
  海量文本        指令-回答对      偏好数据
  学习语言能力    学习遵循指令     学习人类偏好
```

SFT 是让模型从"续写文本"变成"遵循指令回答问题"的关键步骤。没有 SFT 的基座模型（base model）只会续写，不会对话。

我们平时说的"微调"大多指的就是 SFT 这一步。

### 微调数据量多少合适？有没有经验值？

**答： **取决于任务复杂度：

- **简单风格迁移 **（改变回答语气）：100-500 条
- **特定领域问答 **（医疗、法律）：1000-5000 条
- **复杂推理任务 **：5000-50000 条
- **多任务通用能力 **：50000+ 条

经验法则：

- 先用 100 条试跑，看模型是否能学到基本模式
- 逐步增加数据量，观察验证集 loss 的变化
- 如果 loss 不再下降，说明数据量够了或者数据质量有问题

质量永远比数量重要。10 条精心标注的数据 > 100 条随便写的数据。

### 怎么评估微调后的模型效果？

**答： **多维度评估：

1. **自动指标 **：
2. 验证集 loss / perplexity
3. 任务特定指标（分类用 F1，生成用 BLEU/ROUGE）
4. **Benchmark 跑分 **：
5. 通用能力：MMLU、C-Eval
6. 代码能力：HumanEval
7. 数学能力：GSM8K
8. **人工评估 **：
9. 准备 50-100 个测试 case
10. 对比微调前后的回答质量
11. 关注：准确性、完整性、格式、有没有幻觉
12. **A/B 测试 **：
13. 线上灰度，看用户满意度指标

最重要的是第 3 条，人工看 case。自动指标可能骗人。

### 什么是 Merge（模型合并）？LoRA 权重怎么合并回基础模型？

**答： **训练完 LoRA 后，推理时有两种方式：

1. **动态加载 **：基础模型 + LoRA adapter 分开，推理时动态合并（灵活但略慢）
2. **静态合并 **：把 LoRA 权重合并回基础模型，得到一个完整模型（快但不灵活）

合并代码：

```plaintext
from peft import PeftModel

base_model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-7B-Instruct")
peft_model = PeftModel.from_pretrained(base_model, "./lora_weights")

# 合并
merged_model = peft_model.merge_and_unload()
merged_model.save_pretrained("./merged_model")
```

合并后就是一个普通模型，可以直接用 vLLM 等推理框架加载，不需要 PEFT 库。

### 多轮对话数据怎么做微调？loss mask 是什么？

**答： **多轮对话微调时，你只想让模型学习 assistant 的回答，不想让它学习 user 的提问。这就需要 loss mask。

```plaintext
[system] 你是助手     ← mask, 不计算loss
[user] 你好          ← mask, 不计算loss  
[assistant] 你好！    ← 计算loss
[user] 天气怎么样？   ← mask, 不计算loss
[assistant] 今天晴天  ← 计算loss
```

在代码中通过设置 `labels` 实现：被 mask 的位置 label 设为 -100（PyTorch 的 CrossEntropyLoss 会忽略 -100）。

TRL 的 SFTTrainer 如果你传入 messages 格式的数据，它会自动处理 loss mask。

### 什么是 NEFTune？它能提升微调效果吗？

**答： **NEFTune 是在微调时给 embedding 层加随机噪声的技巧：

```python
# 原理很简单
embeddings = model.get_input_embeddings()(input_ids)
noise = torch.zeros_like(embeddings).uniform_(-1, 1)
embeddings = embeddings + noise * alpha / (embeddings.shape[1] ** 0.5)
```

论文显示在多个 benchmark 上能提升 2-5 个点，特别是在数据量较少时效果明显。 在 TRL 中一行开启：

```python
training_args = TrainingArguments(
    ...,
    neftune_noise_alpha=5,  # 推荐值 5-15
)
```

原理可能是噪声起到了正则化作用，防止过拟合。成本几乎为零，建议默认开启试试。

## 模型量化

### 模型量化是什么？为什么要做量化？

**答： **量化就是把模型权重从高精度（FP32/FP16）转换为低精度（INT8/INT4）。

```python
FP32: 32位浮点 → 每个参数 4 字节
FP16: 16位浮点 → 每个参数 2 字节
INT8: 8位整数  → 每个参数 1 字节
INT4: 4位整数  → 每个参数 0.5 字节
```

一个 7B 模型：

- FP16: ~14GB 显存
- INT8: ~7GB 显存
- INT4: ~3.5GB 显存

为什么要量化：

1. 降低显存占用，让消费级显卡也能跑大模型
2. 加速推理（内存带宽是瓶颈，数据量小了自然快）
3. 降低部署成本

### PTQ 和 QAT 有什么区别？

**答：**

**PTQ（Post-Training Quantization，训练后量化） **：

- 模型训练完之后直接量化
- 不需要训练数据（或只需要少量校准数据）
- 速度快，几分钟到几小时
- 精度损失相对大一些

**QAT（Quantization-Aware Training，量化感知训练） **：

- 在训练过程中模拟量化效果
- 需要训练数据和 GPU 算力
- 耗时长
- 精度损失小

PTQ: 训练好的模型 → 直接量化 → 量化模型

QAT: 训练过程中 → 插入伪量化节点 → 模型学会适应量化 → 量化模型

实际中 PTQ 用得更多，因为大模型做 QAT 成本太高。GPTQ、AWQ 都是 PTQ 方法。

### GPTQ、AWQ、GGUF 这几种量化格式有什么区别？

**答：**

| 格式 | 原理 | 运行环境 | 特点 |
| --- | --- | --- | --- |
| GPTQ | 逐层量化，最小化重建误差 | GPU | 精度好，需要校准数据 |
| AWQ | 保护重要权重通道 | GPU | 比GPTQ快，精度相当 |
| GGUF | llama.cpp 的格式 | CPU/GPU混合 | 灵活，支持CPU推理 |
| bitsandbytes | 动态量化 | GPU | 集成在HF生态，用于QLoRA |

选择建议：

- 纯 GPU 推理：AWQ（速度和精度平衡最好）
- CPU 或 CPU+GPU 混合：GGUF（用 llama.cpp 或 Ollama）
- 微调场景：bitsandbytes（配合 QLoRA）

### INT4 量化后精度损失大吗？怎么评估？

**答： **取决于模型大小和量化方法：

- 7B 模型 INT4：perplexity 增加 0.5-1.0，体感上大部分任务影响不大
- 70B 模型 INT4：perplexity 增加 0.1-0.3，几乎无感
- 1-3B 小模型 INT4：损失明显，建议用 INT8

评估方法：

1. 跑 perplexity（越低越好）
2. 跑 benchmark（MMLU、C-Eval 等）
3. 人工对比：准备 50 个测试 case，对比量化前后的回答

经验：模型越大，量化损失越小。70B INT4 的效果可能比 7B FP16 还好。

### 什么是 KV Cache 量化？为什么它很重要？

**答： **KV Cache 是推理时存储的 attention 中间结果，随着序列长度增长线性增加。

KV Cache 显存 = 2 × num_layers × num_heads × head_dim × seq_len × batch_size × dtype_size

对于 70B 模型，4K 上下文的 KV Cache 就要好几 GB。长上下文（128K）时 KV Cache 甚至比模型权重还大。

KV Cache 量化（如 FP8/INT8）可以：

- 减少 50-75% 的 KV Cache 显存
- 支持更长的上下文或更大的 batch size
- 对输出质量影响很小

vLLM 支持 FP8 KV Cache 量化，一行配置就能开启。

### 量化模型怎么用 Ollama 部署？

**答： **Ollama 是最简单的本地部署方案：

```shell
# 直接拉取量化好的模型
ollama pull qwen2.5:7b-instruct-q4_K_M

# 运行
ollama run qwen2.5:7b-instruct-q4_K_M

# API 调用（兼容 OpenAI 格式）
curl http://localhost:11434/v1/chat/completions \
  -d '{"model": "qwen2.5:7b-instruct-q4_K_M", "messages": [{"role": "user", "content": "你好"}]}'
```

Ollama 底层用的 llama.cpp，支持 GGUF 格式。量化级别命名规则：

- `q4_0` ：最基础的 4bit 量化
- `q4_K_M` ：4bit + K-quant 中等精度（推荐）
- `q5_K_M` ：5bit，精度更好但更大
- `q8_0` ：8bit，精度最好

### 什么是混合精度（Mixed Precision）？跟量化有什么关系？

**答： **混合精度是训练时同时使用 FP16 和 FP32：

- 前向传播和反向传播用 FP16（快、省显存）
- 权重更新用 FP32（保持精度）

训练时混合精度:

FP32 权重副本 → 转FP16 → 前向/反向传播(FP16) → 梯度(FP16) → 转FP32 → 更新权重(FP32)

跟量化的区别：

- 混合精度是 **训练 **技术，目的是加速训练
- 量化是 **推理 **技术（主要），目的是压缩模型

现在训练基本都用 BF16（Brain Float 16），比 FP16 数值范围更大，不容易溢出。

### AWQ 的核心思想是什么？为什么比 GPTQ 快？

**答： **AWQ（Activation-aware Weight Quantization）的核心观察：不是所有权重都同等重要，1% 的"显著权重"对模型输出影响巨大。

做法：

1. 用少量校准数据找出哪些权重通道对激活值影响大
2. 对这些重要通道做缩放保护（乘以一个大系数再量化，减少相对误差）
3. 其他通道正常量化

比 GPTQ 快的原因：GPTQ 需要逐层做矩阵分解和优化，计算量大；AWQ 只需要统计激活值分布然后做缩放，简单得多。量化一个 7B 模型，GPTQ 要几十分钟，AWQ 几分钟就行。

### 量化对不同类型任务的影响一样吗？

**答： **不一样，影响程度：

- **简单问答/闲聊 **：影响最小，INT4 基本无感
- **数学推理 **：影响中等，精度敏感的计算可能出错
- **代码生成 **：影响中等，语法错误可能增加
- **长文本理解 **：影响较大，上下文越长量化误差累积越多
- **多语言 **：低资源语言受影响更大

建议：如果你的场景对精度要求高（比如医疗、法律），用 INT8 或 FP8；一般场景 INT4 够用。

### FP8 量化是什么？跟 INT8 有什么区别？

**答： **FP8 是 8 位浮点数，有两种格式：

- **E4M3 **：4位指数+3位尾数，范围大，适合权重
- **E5M2 **：5位指数+2位尾数，范围更大，适合梯度

跟 INT8 的区别：

- INT8 是均匀量化，所有区间精度一样
- FP8 是非均匀量化，接近 0 的地方精度更高

FP8 的优势：不需要校准数据，直接转换就行（类似 FP16→FP32 的转换）。

H100/4090 等新卡原生支持 FP8 计算，速度跟 INT8 一样快但精度更好。

vLLM 已经支持 FP8 推理，是目前 GPU 推理的最佳量化选择之一。

## 模型部署与推理优化

### vLLM 是什么？为什么它推理这么快？

**答： **vLLM 是目前最流行的 LLM 推理引擎，核心创新是 PagedAttention：

```shell
传统方式: 为每个请求预分配连续的 KV Cache 显存
         → 显存碎片化严重，利用率低

PagedAttention: 像操作系统的虚拟内存一样管理 KV Cache
         → 按需分配，非连续存储，显存利用率接近 100%
```

其他优化：

- **Continuous Batching **：不等一个 batch 全部完成，有请求完成就立即填入新请求
- **Tensor Parallelism **：多卡并行
- **Prefix Caching **：相同前缀的请求共享 KV Cache
- **Speculative Decoding **：投机采样加速

效果：比 HuggingFace Transformers 原生推理快 10-24 倍。

### Tensor Parallelism 和 Pipeline Parallelism 有什么区别？

**答：**

```shell
Tensor Parallelism (TP): 把一层切分到多张卡
┌─────────────────────────────────┐
│           Layer N                │
│  ┌───────┐  ┌───────┐          │
│  │ GPU 0 │  │ GPU 1 │  ...     │  ← 每层的矩阵横切/纵切
│  └───────┘  └───────┘          │
└─────────────────────────────────┘

Pipeline Parallelism (PP): 把不同层放到不同卡
┌─────────┐  ┌─────────┐  ┌─────────┐
│ Layer 0-7│→│Layer 8-15│→│Layer16-23│  ← 不同层在不同卡
│  GPU 0   │  │  GPU 1   │  │  GPU 2   │
└─────────┘  └─────────┘  └─────────┘
```

选择：

- TP 需要卡间高速互联（NVLink），延迟低但通信量大
- PP 通信量小但有 pipeline bubble（某些卡空闲等待）
- 实际中常组合使用：节点内 TP，节点间 PP

vLLM 主要用 TP，因为推理场景对延迟敏感。

### 什么是 Continuous Batching？为什么比 Static Batching 好？

**答：**

```shell
Static Batching:
请求1: ████████████░░░░░░  (等最长的完成)
请求2: ████████░░░░░░░░░░  (早完成了还得等)
请求3: ████████████████████ (最长的那个)
                          ↑ 整个batch一起返回
                          

Continuous Batching:
请求1: ████████████ → 返回，立即填入新请求5
请求2: ████████ → 返回，立即填入新请求4
请求3: ████████████████████ → 返回
请求4:         ████████████ → 返回
请求5:             ██████████ → 返回
```

Static Batching 的问题：短请求要等长请求完成才能返回，GPU 利用率低。

Continuous Batching 在每个 iteration 级别做调度，有请求完成就立即释放资源并填入新请求。吞吐量提升 2-5 倍。

### Speculative Decoding（投机采样）是什么原理？

**答： **核心思想：用一个小模型（draft model）快速生成多个 token，然后用大模型一次性验证。

```shell
传统自回归: 大模型生成 token1 → token2 → token3 → ... (每步都要跑大模型)

投机采样:
小模型快速生成: token1, token2, token3, token4, token5
大模型一次性验证这5个token (一次前向传播)
如果前3个对了，第4个错了 → 接受前3个，从第4个重新来

加速比 = 小模型生成N个token的时间 + 大模型验证1次的时间
        vs 大模型生成N个token的时间(N次前向传播)
```

效果：在大模型和小模型能力差距不太大时，加速 2-3 倍，且输出分布与大模型完全一致（数学上可证明）。

### 什么是 Prefix Caching？什么场景下收益最大？

**答： **Prefix Caching 是把相同前缀的 KV Cache 缓存起来复用。

```shell
请求1: [System Prompt] + [用户问题A]  → 计算完整 KV Cache
请求2: [System Prompt] + [用户问题B]  → System Prompt 部分直接复用缓存！
```

收益最大的场景：

- **长 System Prompt **：比如 RAG 场景，system prompt 里塞了大量文档
- **多轮对话 **：前面的对话历史是共享前缀
- **批量处理 **：同一个模板处理不同数据

vLLM 开启方式： `--enable-prefix-caching`

如果你的 system prompt 有 2000 tokens，100 个并发请求就能省掉 200K tokens 的重复计算。

### 模型推理的延迟瓶颈在哪？怎么优化？

**答： **LLM 推理分两个阶段：

Prefill 阶段: 处理输入 prompt (计算密集型，GPU算力是瓶颈)

Decode 阶段: 逐token生成 (内存带宽密集型，显存带宽是瓶颈)

优化手段：

| 阶段 | 瓶颈 | 优化方法 |
| --- | --- | --- |
| Prefill | GPU 算力 | Flash Attention、量化、更大batch |
| Decode | 显存带宽 | 量化(减少数据搬运)、GQA、投机采样 |
| 整体 | 调度 | Continuous Batching、Prefix Caching |

对于交互式应用，用户感知的是 TTFT（Time To First Token，首 token 延迟）和 TPS（Tokens Per Second，生成速度）。TTFT 取决于 prefill 速度，TPS 取决于 decode 速度。

### GQA（Grouped Query Attention）是什么？为什么新模型都用它？

**答：**

```shell
MHA (Multi-Head Attention):     每个 head 都有独立的 K、V
                                KV Cache 大，推理慢

MQA (Multi-Query Attention):    所有 head 共享一组 K、V
                                KV Cache 最小，但精度损失大

GQA (Grouped Query Attention):  每组 head 共享一组 K、V
                                折中方案！
                                
┌─────────────────────────────────────┐
│ MHA:  Q1 Q2 Q3 Q4 Q5 Q6 Q7 Q8      │
│       K1 K2 K3 K4 K5 K6 K7 K8      │  8组KV
│                                      │
│ GQA:  Q1 Q2 Q3 Q4 Q5 Q6 Q7 Q8      │
│       K1    K2    K3    K4          │  4组KV (2个Q共享1个KV)
│                                      │
│ MQA:  Q1 Q2 Q3 Q4 Q5 Q6 Q7 Q8      │
│       K1                            │  1组KV
└─────────────────────────────────────┘
```

GQA 把 KV Cache 减少到 MHA 的 1/N（N 是每组的 head 数），推理速度提升明显，精度损失很小。Llama 2 70B、Qwen2、Mistral 等新模型都用 GQA。

### Flash Attention 是什么？为什么能加速？

**答： **Flash Attention 的核心是优化 GPU 内存访问模式。

传统 Attention 的问题：

```shell
Q×K^T → 写入 HBM → Softmax → 写入 HBM → ×V → 写入 HBM
       (慢)              (慢)              (慢)
```

Flash Attention：

```shell
在 SRAM (片上高速缓存) 中完成所有计算，只写一次 HBM
通过分块(tiling)技术，每次只处理一小块，在SRAM中完成 Q×K^T → Softmax → ×V
```

```shell
GPU 内存层次:
┌─────────────┐
│ SRAM (20MB) │  ← 快 (19TB/s)，Flash Attention 在这里算
├─────────────┤
│ HBM (80GB)  │  ← 慢 (3TB/s)，传统方法反复读写这里
└─────────────┘
```

效果：2-4 倍加速，显存从 O(N²) 降到 O(N)。现在基本是标配，vLLM、HuggingFace 都默认开启。

### 怎么选择部署方案？什么时候用云 API，什么时候自部署？

**答： **决策矩阵：

| 因素 | 用云 API | 自部署 |
| --- | --- | --- |
| 数据隐私 | 不敏感 | 敏感数据必须自部署 |
| 调用量 | 少（<10万次/天） | 大（>10万次/天） |
| 定制需求 | 通用模型够用 | 需要微调模型 |
| 延迟要求 | 可接受网络延迟 | 需要极低延迟 |
| 团队能力 | 没有 GPU 运维经验 | 有 infra 团队 |

成本拐点：大概在日调用 5-10 万次时，自部署开始比 API 便宜。但要算上 GPU 租赁、运维人力、故障风险等隐性成本。

混合方案也很常见：核心业务自部署，长尾需求用 API。

### 什么是模型蒸馏（Knowledge Distillation）？跟量化有什么区别？

**答：**

蒸馏：用大模型（teacher）的输出来训练小模型（student）

```shell
┌────────────┐
│ Teacher    │  (如 GPT-4, 72B)
│ 大模型     │──→ 输出概率分布 (soft labels)
└────────────┘         │
                       ▼
              ┌────────────────┐
              │ Student 小模型  │  学习模仿 teacher 的输出
              │ (如 7B)        │
              └────────────────┘
```

跟量化的区别：

- **量化 **：同一个模型，降低精度，架构不变
- **蒸馏 **：换一个更小的模型，架构可以不同

两者可以叠加：先蒸馏得到小模型，再量化进一步压缩。

实际应用：很多开源小模型（如 Phi、Gemma）都用了大模型的合成数据训练，本质就是蒸馏。

### 多模型部署时怎么做路由？

**答： **常见策略：

```shell
┌──────────┐     ┌──────────────┐
│  Router  │     │ 简单问题 → 小模型 (7B, 快且便宜)
│  路由器   │────→│ 复杂问题 → 大模型 (72B, 慢但准)
│          │     │ 特定领域 → 专用微调模型
└──────────┘     └──────────────┘
```

路由方式：

1. **规则路由 **：根据问题长度、关键词、用户等级
2. **分类器路由 **：训练一个小分类模型判断问题难度
3. **级联路由 **：先用小模型回答，置信度低时升级到大模型

好处：在保持质量的同时大幅降低平均成本。实测 70-80% 的请求小模型就能搞定。

### Docker 部署 LLM 服务有哪些注意事项？

**答：**

```shell
# 基础镜像选择
FROM vllm/vllm-openai:latest

# 或者自建
FROM nvidia/cuda:12.4.0-runtime-ubuntu22.04
```

关键注意事项：

1. **GPU 透传 **： `docker run --gpus all` 或指定 `--gpus '"device=0,1"'`
2. **共享内存 **： `--shm-size=16g` ，模型加载需要大量共享内存
3. **模型缓存 **：把模型目录挂载进去，别每次都下载
4. **健康检查 **：配置 healthcheck，模型加载需要时间
5. **资源限制 **：设置显存上限防止 OOM 影响其他服务

```yaml
# docker-compose.yml
services:
  vllm:
    image: vllm/vllm-openai:latest
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 2
              capabilities: [gpu]
    volumes:
      - ./models:/models
    shm_size: '16gb'
    command: >
      --model /models/Qwen2.5-7B-Instruct
      --tensor-parallel-size 2
```
