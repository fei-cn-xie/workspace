### 从零搭建一个生产级 RAG 系统，你的技术选型是什么？

**答： **我的选型：

```shell
┌─────────────────────────────────────────────────────┐
│                    架构总览                           │
├─────────────────────────────────────────────────────┤
│                                                      │
│  文档处理: MinerU /unstructured / marker (PDF解析)   │
│  分块: LlamaIndex NodeParser (语义分块)              │
│  Embedding: text-embedding-v3 或 qwen-embedding
│  向量库: Milvus (支持 hybrid search)                 │
│  Reranker: bge-reranker-v2-m3                       │
│  LLM: Qwen2.5-72B-Instruct (vLLM部署)              │
│  编排: LangChain/LangGraph (状态管理+流程控制)       │
│  API: FastAPI + SSE streaming                       │
│  监控: LangSmith + Prometheus + Grafana             │
│  缓存: Redis (语义缓存+结果缓存)                     │
│                                                      │
└─────────────────────────────────────────────────────┘
```

关键设计决策：

- Milvus 而非 Pinecone：自部署可控，支持 hybrid search
- LangGraph 而非纯 LlamaIndex：需要复杂的多步检索逻辑
- 自部署模型而非 API：数据隐私要求 + 成本考虑

### 一个 RAG 系统上线后效果不好，你怎么排查？

**答： **按流程逐步排查：

```shell
用户反馈"回答不准" → 是哪个环节的问题？

检索问题？
└→ 看检索到的文档是否相关
└→ 如果不相关：embedding模型不行 / 分块策略有问题 / 需要query改写

生成问题？
└→ 检索到了正确文档但回答不对
└→ prompt 需要优化 / 上下文太长模型抓不住重点 / 需要加 reranker

数据问题？
└→ 知识库里根本没有相关信息
└→ 补充数据源 / 告诉用户"我不知道"
```

**实操步骤：**

1. 先看 LangSmith trace，定位是检索还是生成的问题
2. 抽样 50 个 bad case，分类统计
3. 针对最大类别的问题优化
4. A/B 测试验证效果

### 怎么实现语义缓存（Semantic Cache）？

**答： **语义缓存是把相似问题的答案缓存起来，避免重复调用 LLM。

```python
import numpy as np
from redis import Redis

class SemanticCache:
    def init(self, threshold=0.92):
        self.threshold = threshold
        self.redis = Redis()

    def get(self, query: str):
        query_embedding = embed(query)
        # 在缓存的 embedding 中找最相似的
        cached = self.redis.ft("cache_idx").search(
            query_vector=query_embedding,
            top_k=1
        )
        if cached and cached[0].score > self.threshold:
            return cached[0].answer
        return None

    def set(self, query: str, answer: str):
        embedding = embed(query)
        self.redis.hset(f"cache:{hash(query)}", mapping={
            "embedding": embedding.tobytes(),
            "answer": answer,
            "query": query
        })
```

注意事项：

- 阈值要调好，太低会返回不相关的缓存
- 要设置 TTL，知识库更新后缓存要失效
- 适合高频重复问题的场景（如客服）

### 大模型的 Context Window 越来越长（128K、1M），RAG 还有必要吗？

**答： **还是有必要的，原因：

1. **成本 **：128K context 的 API 调用费用很高，RAG 只传相关片段更省钱
2. **Lost in the Middle **：研究表明模型对长上下文中间部分的信息利用率低
3. **实时性 **：RAG 可以检索最新数据，长上下文不能
4. **精确性 **：精准检索 Top-5 相关段落 > 把整本书塞进去
5. **可解释性 **：RAG 能告诉你答案来自哪个文档

但长上下文确实改变了 RAG 的做法：

- 可以检索更多 chunks（Top-20 而非 Top-5）
- 可以把整个文档而非片段传入
- 对分块策略的要求降低了

结论：RAG 不会消失，但会演化。长上下文是 RAG 的补充而非替代。

### 怎么处理多模态 RAG（图片、表格）？

**答： **几种方案：

1. **图片转文本 **：用 VLM（如 GPT-4o）把图片描述成文本，再做常规 RAG
2. **多模态 Embedding **：用 CLIP 等模型同时 embed 文本和图片
3. **表格结构化 **：把表格转成 markdown 或 JSON，保留结构信息

```shell
┌──────────┐     ┌───────────────┐     ┌──────────────┐
│  PDF文档  │────→│  解析器        │────→│ 文本chunks   │──→ 文本向量库
│ (含图表)  │     │ (unstructured) │     │ 图片描述     │──→ 多模态向量库
└──────────┘     └───────────────┘     │ 表格markdown │──→ 文本向量库
                                       └──────────────┘
```

实践建议：

- 表格用 markdown 格式存储效果最好
- 图片先用 VLM 生成描述，描述和原图都存
- 检索时返回原图让 VLM 直接看，比只看描述准确

### 训练和推理时的显存占用分别由什么决定？

**答：**

训练显存 = 模型参数 + 梯度 + 优化器状态 + 激活值

```shell
以 7B 模型 FP16 训练为例:
模型参数:     7B × 2 bytes = 14 GB
梯度:         7B × 2 bytes = 14 GB
Adam优化器:   7B × 2 × 4 bytes = 56 GB (两个动量 + FP32副本)
激活值:       取决于 batch size 和序列长度，几GB到几十GB
─────────────────────────────────
总计:         ~90-100 GB (这就是为什么要用 LoRA)
```

推理显存 = 模型参数 + KV Cache

```shell
以 7B 模型 FP16 推理为例:
模型参数:     14 GB
KV Cache:     取决于 batch_size × seq_len
              单请求4K上下文约 1-2 GB
─────────────────────────────────
总计:         ~16 GB (一张 4090 就够)
```

这就是为什么训练比推理贵得多。

### 什么是 MoE（Mixture of Experts）？为什么 Mixtral 推理快？

**答： **MoE 的核心：不是所有参数都参与每次计算，只激活一部分"专家"。

```shell
┌─────────────────────────────────────┐
│            Router (门控网络)          │
│         选择 Top-K 个专家            │
└──────┬────────┬────────┬────────────┘
       │        │        │
       ▼        ▼        ▼
┌──────────┐ ┌──────────┐ ┌──────────┐
│ Expert 1 │ │ Expert 2 │ │ Expert 3 │ ... Expert 8
│ (激活✓)  │ │ (激活✓)  │ │ (未激活)  │
└──────────┘ └──────────┘ └──────────┘
```

**Mixtral 8x7B **：

- 总参数量：47B
- 每次推理激活参数：~13B（只用 2 个专家）
- 效果接近 70B 密集模型
- 推理速度接近 13B 模型

为什么快：虽然模型大，但每个 token 只经过 2 个专家的 FFN 层，计算量小。缺点是显存还是要装下全部 47B 参数。

### 大模型应用的安全问题有哪些？怎么防护？

**答： **主要风险：

1. **Prompt Injection **：用户通过精心构造的输入绕过系统指令
2. 防护：输入过滤 + 输出检查 + 权限最小化
3. **数据泄露 **：模型把训练数据或其他用户数据吐出来
4. 防护：不在 prompt 中放敏感信息 + 输出过滤
5. **幻觉导致的错误决策 **：模型自信地给出错误信息
6. 防护：RAG 溯源 + 人工审核关键决策
7. **滥用 **：用模型生成有害内容
8. 防护：内容审核 API + 使用限制
9. **Agent 越权 **：Agent 执行了不该执行的操作
10. 防护：工具权限控制 + Human-in-the-loop + 沙箱执行

```python
# 简单的输出过滤示例
def filter_output(response: str, sensitive_patterns: list) -> str:
    for pattern in sensitive_patterns:
        if pattern in response:
            return "抱歉，我无法回答这个问题。"
    return response
```

### 未来 1-2 年，大模型技术你最看好哪些方向？

**答： **几个我认为会爆发的方向：

1. **Agent 落地 **：从 demo 到生产，LangGraph 这类框架会越来越成熟。关键是可靠性和可控性的提升。
2. **端侧模型 **：手机/PC 上跑的小模型（1-3B），配合量化技术，隐私和延迟都有优势。Apple Intelligence、高通 NPU 都在推。
3. **长上下文 + RAG 融合 **：不是二选一，而是结合使用。长上下文处理文档级理解，RAG 处理知识库级检索。
4. **多模态 Agent **：能看屏幕、操作电脑的 Agent（如 Claude Computer Use），会改变人机交互方式。
5. **推理优化 **：更高效的推理引擎、更好的量化方法、投机采样的改进，让大模型部署成本持续下降。
6. **合成数据 + 蒸馏 **：用大模型生成训练数据来训练小模型，形成正循环。

面试时说这个问题，关键是要有自己的判断和理由，不要只列方向。
