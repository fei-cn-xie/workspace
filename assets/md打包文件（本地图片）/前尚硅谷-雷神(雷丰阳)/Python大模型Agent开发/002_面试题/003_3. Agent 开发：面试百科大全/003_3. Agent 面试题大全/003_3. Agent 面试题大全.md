# 3. Agent 面试题大全

### LangChain 最新版的核心架构是什么样的？LCEL 还在用吗？

**答： **LCEL（LangChain Expression Language）已经废弃了。现在 LangChain 的架构是：

- **langchain-core **：基础抽象（BaseMessage、BaseTool、Runnable 等）
- **langchain **：高层组件（各种 Chain、Retriever）
- **langchain-community **：社区集成
- **langgraph **：Agent 和工作流编排（这是现在的重点）

现在官方推荐用 LangGraph 来构建 Agent 和复杂工作流，而不是用老的 AgentExecutor 或 LCEL chain。LangGraph 提供了更细粒度的状态管理和流程控制。

如果构建现代应用，则直接使用 LangChain 的 `create_agent` 。他会在底层基于LangGraph构建出整个智能体工作流。

### LangGraph 的核心概念是什么？画个图说说。

**答： **LangGraph 本质是一个状态机框架，核心概念：

```plaintext

┌─────────────────────────────────────────┐
│              StateGraph                   │
│                                           │
│   ┌───────┐    ┌───────┐    ┌───────┐   │
│   │ Node1 │───→│ Node2 │───→│ Node3 │   │
│   └───────┘    └───┬───┘    └───────┘   │
│                     │                     │
│                     ▼                     │
│               ┌───────────┐              │
│               │ Conditional│              │
│               │   Edge     │              │
│               └─────┬─────┘              │
│                     │                     │
│              ┌──────┴──────┐             │
│              ▼             ▼              │
│         ┌───────┐    ┌───────┐           │
│         │ NodeA │    │ NodeB │           │
│         └───────┘    └───────┘           │
│                                           │
│   State: TypedDict 在节点间传递和更新      │
└─────────────────────────────────────────┘
```

- **State **：一个 TypedDict，所有节点共享和更新。用来作为工作流期间的 **状态机对象 **（也就是保存数据的对象）
- **Node **：处理函数，接收 state 返回更新（每个节点做完事情，更新状态机）
- **Edge **：节点间的连接，可以是固定的或条件的（工作流的执行顺序）
- **Conditional Edge **：根据 state 决定下一步走哪个节点（条件边）

### 用 LangChain 写一个最简单的 ReAct Agent 是什么样的？

**答：**

```python
from langchain_openai import ChatOpenAI
from langchain_core.tools import tool

@tool
def search(query: str) -> str:
    """搜索互联网"""
    return f"搜索结果: {query} 的相关信息..."

@tool
def calculator(expression: str) -> str:
    """计算数学表达式"""
    return str(eval(expression))

llm = ChatOpenAI(model="gpt-4o")
agent = create_agent(llm, tools=[search, calculator])

result = agent.invoke({"messages": [("user", "北京今天气温多少度？")]})
```

`create_agent` 是 LangChain 预置的 ReAct 模式实现，内部就是一个循环：

**LLM 决定调用工具 → 执行工具 → 把结果反馈给 LLM → 直到 LLM 决定直接回答。**

### LangGraph 的 State 怎么设计？Annotated 是干嘛的？

**答：**

```python
from typing import Annotated, TypedDict
from langgraph.graph.message import add_messages

class AgentState(TypedDict):
    messages: Annotated[list, add_messages]  # 消息列表，用 add_messages 做 reducer
    context: str                              # 普通字段，直接覆盖
    iteration_count: int
```

`Annotated` 里的第二个参数是 reducer 函数，决定了当多个节点更新同一个字段时怎么合并。 `add_messages` 是追加消息而不是覆盖。如果不加 Annotated，默认行为是后写覆盖。

这个设计很重要，特别是在有并行节点的时候，reducer 决定了状态怎么合并。

### langgraph 的 checkpointer 是干嘛的？怎么实现对话持久化？

**答： **Checkpointer 用来持久化 graph 的状态，实现：

- 对话历史持久化（重启后能恢复）
- Human-in-the-loop（暂停等待人工审批）
- 时间旅行（回到之前的某个状态）

```python
from langgraph.checkpoint.memory import MemorySaver
from langgraph.checkpoint.postgres import PostgresSaver

# 开发用内存
memory = MemorySaver()

# 生产用 Postgres
checkpointer = PostgresSaver.from_conn_string("postgresql://...")

graph = builder.compile(checkpointer=checkpointer)

# 调用时传 thread_id 来区分不同对话
config = {"configurable": {"thread_id": "user_123"}}
result = graph.invoke({"messages": [("user", "你好")]}, config)
```

注意：如果在 LangChain 中使用，则更加简单

### LangGraph 怎么实现 Human-in-the-loop？

**答： **用 `interrupt` 函数：

```python
from langgraph.types import interrupt, Command

def sensitive_action(state):
    # 执行敏感操作前暂停，等待人工确认
    approval = interrupt("即将删除数据库记录，是否继续？")

    if approval == "yes":
        # 执行操作
        return {"result": "已删除"}
    else:
        return {"result": "已取消"}
```

graph 执行到 `interrupt` 时会暂停，返回给调用方。调用方拿到人工输入后，用 `Command(resume="yes")` 恢复执行。配合 checkpointer 使用，暂停期间状态不会丢失。

如果是LangChain中，直接使用 create_agent 函数的 interrupt_on 参数指定HITL规则

### LangGraph 中怎么做子图（Subgraph）？什么场景需要？

**答： **子图就是把一个完整的 graph 作为另一个 graph 的节点：

```plaintext
# 定义子图
sub_builder = StateGraph(SubState)
sub_builder.add_node("step1", step1_fn)
sub_builder.add_node("step2", step2_fn)
sub_builder.add_edge("step1", "step2")
sub_graph = sub_builder.compile()

# 在父图中使用
parent_builder = StateGraph(ParentState)
parent_builder.add_node("sub_process", sub_graph)
```

适用场景：

- 复杂工作流拆分，每个子图负责一个独立任务
- 多 Agent 协作，每个 Agent 是一个子图
- 复用：同一个子图在不同父图中使用

### 什么是 Multi-Agent 架构？LangGraph 怎么实现？

**答： **Multi-Agent 就是多个专业化的 Agent 协作完成任务。常见模式：

```plaintext

┌─────────────────────────────────────┐
│           Supervisor Agent           │
│         (路由和协调)                  │
└──────┬──────────┬──────────┬────────┘
       │          │          │
       ▼          ▼          ▼
┌──────────┐ ┌──────────┐ ┌──────────┐
│ Research │ │  Coder   │ │ Reviewer │
│  Agent   │ │  Agent   │ │  Agent   │
└──────────┘ └──────────┘ └──────────┘
```

LangChain 实现方式：每个 Agent 是 工具，Supervisor 做意图识别，根据任务类型调用不同的 Agent 工具。

### LangChain 的 Tool 怎么定义？有几种方式？

**答： **最新版主要两种方式：

```python
# 方式1：@tool 装饰器（最常用）
from langchain_core.tools import tool

@tool
def get_weather(city: str, date: str = "today") -> str:
    """获取指定城市的天气信息。
    
    Args:
        city: 城市名称
        date: 日期，默认今天
    """
    return f"{city} {date} 晴 25°C"

# 方式2：继承 BaseTool（需要更多控制时）
from langchain_core.tools import BaseTool
from pydantic import BaseModel, Field

class SearchInput(BaseModel):
    query: str = Field(description="搜索关键词")
    top_k: int = Field(default=5, description="返回结果数")

class SearchTool(BaseTool):
    name: str = "search"
    description: str = "搜索知识库"
    args_schema: type = SearchInput
    
    def _run(self, query: str, top_k: int = 5) -> str:
        return "搜索结果..."
```

### LangGraph 怎么处理错误和重试？

**答： **几个层面：

1. **节点级别的 try-catch **：在节点函数内部处理异常
2. **工具错误处理 **：工具调用失败时返回错误信息让 LLM 重新决策

```python
def tool_node(state):
    try:
        result = execute_tool(state["tool_call"])
        return {"messages": [ToolMessage(content=result)]}
    except Exception as e:
        # 把错误信息返回给 LLM，让它决定怎么办
        return {"messages": [ToolMessage(content=f"工具执行失败: {e}")]}
```

1. **循环次数限制 **：通过 state 中的计数器 + conditional edge 实现

```python
def should_continue(state):
    if state["iteration_count"] > 5:
        return "end"  # 防止无限循环
    if state["messages"][-1].tool_calls:
        return "tools"
    return "end"
```

### 什么是 Tool Calling？跟 Function Calling 有什么区别？

**答： **本质上是一回事，Tool Calling 是更通用的叫法。Function Calling 是 OpenAI 最早的命名，后来大家都叫 Tool Calling 了。

核心机制：你把工具的 schema（名称、描述、参数）告诉 LLM，LLM 根据用户意图决定是否调用工具、调用哪个、传什么参数。LLM 不是真的执行工具，它只是输出一个结构化的调用请求，由你的代码来实际执行。

```plaintext
用户: "北京天气怎么样？"
LLM输出: tool_call(name="get_weather", args={"city": "北京"})
你的代码: 调用天气API → 返回结果
LLM: 根据结果生成自然语言回答
```

### LangGraph 的 streaming 怎么做？

**答： **LangGraph 支持多种粒度的 streaming：

```python
# 1. 节点级别 streaming：每个节点完成时输出
async for event in graph.astream(inputs, config):
    print(event)  # 每个节点的输出

# 2. Token 级别 streaming：LLM 生成过程中逐 token 输出
async for event in graph.astream_events(inputs, config, version="v2"):
    if event["event"] == "on_chat_model_stream":
        print(event["data"]["chunk"].content, end="")
```

生产环境中一般用 `astream_events` ，因为用户体验需要看到逐字输出。配合 FastAPI 的 StreamingResponse 就能实现 SSE 推送。

### DeepAgents 是什么概念？跟普通 Agent 有什么区别？

**答： **DeepAgents 指的是具备深度推理和规划能力的 Agent 系统。跟普通 ReAct Agent 的区别：

- **普通 Agent **：一步一步 think-act-observe，比较浅层
- **DeepAgents **：具备长期规划、任务分解、自我反思、记忆管理等能力

关键特征：

1. **规划能力 **：能把复杂任务分解成子任务树
2. **反思机制 **：执行后评估效果，必要时调整策略
3. **长期记忆 **：跨对话保持上下文和学到的经验
4. **工具创造 **：能自己编写和注册新工具

LangChain 是实现 DeepAgents 的底层框架，DeepAgents 比原生Agent内置了核心工具能力

### LangGraph 怎么做并行执行？

**答： **用 `Send` API 实现 map-reduce 模式：

```python
from langgraph.types import Send

def fan_out(state):
    # 把任务分发给多个并行节点
    return [
        Send("process_item", {"item": item}) 
        for item in state["items"]
    ]

builder.add_conditional_edges("start", fan_out)
```

或者直接在图中定义并行边：

```python
# node_a 和 node_b 会并行执行
builder.add_edge("start", "node_a")
builder.add_edge("start", "node_b")
builder.add_edge(["node_a", "node_b"], "merge")  # 都完成后汇合
```

并行执行时 state 的合并靠 reducer 函数处理。

### LangChain 的 Structured Output 怎么用？

**答： **让 LLM 输出结构化数据，用 `with_structured_output` ：

```python
from pydantic import BaseModel, Field
from langchain_openai import ChatOpenAI

class MovieReview(BaseModel):
    title: str = Field(description="电影名称")
    rating: float = Field(description="评分1-10")
    summary: str = Field(description="一句话总结")

llm = ChatOpenAI(model="gpt-4o")
structured_llm = llm.with_structured_output(MovieReview)

result = structured_llm.invoke("评价一下《星际穿越》")
print(result.title)   # 星际穿越
print(result.rating)  # 9.2
```

底层是通过 tool calling 实现的——把 Pydantic schema 转成 tool schema，强制 LLM 以这个格式输出。

### 生产环境部署 LangGraph Agent 有哪些注意事项？

**答：**

1. **超时控制 **：LLM 调用和工具执行都要设超时，防止卡死
2. **循环限制 **：设置最大迭代次数，防止 Agent 陷入死循环
3. **成本控制 **：监控 token 用量，设置单次对话的 token 上限
4. **可观测性 **：接入 LangSmith 或自建 tracing，记录每一步的输入输出
5. **错误恢复 **：用 checkpointer 持久化状态，崩溃后能恢复
6. **并发控制 **：多用户场景下 thread_id 隔离，注意共享资源的锁

LangGraph 官方提供了 LangGraph Platform（原 LangServe），可以直接部署为 API 服务，自带这些生产级特性。

### LangChain 的 Callback 机制是怎么工作的？

**答： **Callback 是 LangChain 的可观测性机制，在各个生命周期事件触发回调：

```python
from langchain_core.callbacks import BaseCallbackHandler

class MyHandler(BaseCallbackHandler):
    def on_llm_start(self, serialized, prompts, **kwargs):
        print(f"LLM 开始调用，prompt: {prompts[0][:50]}...")
    
    def on_tool_start(self, serialized, input_str, **kwargs):
        print(f"工具调用: {serialized['name']}, 输入: {input_str}")
    
    def on_llm_end(self, response, **kwargs):
        print(f"LLM 返回: {response.generations[0][0].text[:50]}...")

# 使用
llm.invoke("你好", config={"callbacks": [MyHandler()]})
```

LangSmith 就是基于 callback 机制实现的全链路追踪。

### 怎么给 LangGraph Agent 加记忆（Memory）？

**答： **两种层面的记忆：

1. **短期记忆（对话历史） **：通过 checkpointer + thread_id 自动管理
2. **长期记忆（跨对话） **：用 LangGraph 的 Store：

```python
from langgraph.store.memory import InMemoryStore

store = InMemoryStore()

# 在节点中读写长期记忆
def my_node(state, config, store):
    user_id = config["configurable"]["user_id"]
    
    # 读取记忆
    memories = store.search(("memories", user_id))
    
    # 写入新记忆
    store.put(("memories", user_id), "pref_1", {"content": "用户喜欢简洁回答"})
    
    return state

graph = builder.compile(checkpointer=checkpointer, store=store)
```

### LangGraph 和 CrewAI、AutoGen 这些框架比，优势在哪？

**答：**

| 维度 | LangGraph | CrewAI | AutoGen |
| --- | --- | --- | --- |
| 控制粒度 | 最细，完全自定义 | 中等，角色驱动 | 中等，对话驱动 |
| 状态管理 | 显式 TypedDict | 隐式 | 隐式 |
| 可调试性 | 好，每步可追踪 | 一般 | 一般 |
| 学习曲线 | 较陡 | 平缓 | 中等 |
| 生产就绪 | 是 | 还在成熟 | 还在成熟 |

LangGraph 的核心优势是 **可控性 **和 **可观测性 **。你能精确控制每一步的逻辑，出了问题能定位到具体节点。缺点是代码量比 CrewAI 多。

如果是快速原型，CrewAI 更快；如果是生产系统，LangGraph 更稳。

### OpenAI 的 Assistants API 和自己用 LangGraph 搭 Agent 有什么区别？

**答：**

Assistants API 是托管方案：

- 优点：开箱即用，自带文件检索、代码解释器、对话管理
- 缺点：黑盒，不能自定义检索策略，只能用 OpenAI 模型，成本不透明

LangGraph 自建：

- 优点：完全可控，可以用任何模型，自定义每个环节
- 缺点：需要自己搞基础设施

选择建议：如果你的场景简单（比如就是文档问答），Assistants API 够用。如果需要复杂工作流、多模型、自定义检索、或者对成本敏感，自建更好。

### Prompt Engineering 在 Agent 系统中有哪些最佳实践？

**答：**

1. **System Prompt 要明确角色和边界 **：告诉 Agent 它是谁、能做什么、不能做什么
2. **工具描述要精确 **：LLM 靠工具描述决定何时调用，描述模糊会导致误调用
3. **Few-shot 示例 **：给几个工具调用的正确示例，特别是复杂参数的工具
4. **输出格式约束 **：明确要求输出格式，减少解析失败
5. **思考链引导 **：在 system prompt 中要求 Agent 先分析再行动

你是一个数据分析助手。在回答问题前，请先：

1. 分析用户需要什么数据
2. 确定需要调用哪些工具
3. 按顺序执行
4. 综合结果给出回答

如果信息不足，主动询问用户，不要猜测。

### LangGraph 中怎么实现 Plan-and-Execute 模式？

**答： **Plan-and-Execute 是先规划再执行的模式：

```python
┌──────────┐     ┌──────────┐     ┌──────────┐
│  Planner │────→│ Executor │────→│ Replanner│──┐
│  (规划)   │     │  (执行)   │     │  (重规划) │  │
└──────────┘     └──────────┘     └────┬─────┘  │
                                       │         │
                                       └─────────┘
                                    (未完成则继续)
class PlanState(TypedDict):
    messages: Annotated[list, add_messages]
    plan: list[str]       # 步骤列表
    current_step: int
    results: list[str]

def planner(state):
    plan = llm.invoke("把以下任务分解为步骤: ...")
    return {"plan": plan.steps}

def executor(state):
    step = state["plan"][state["current_step"]]
    result = agent.invoke(step)
    return {"results": [result], "current_step": state["current_step"] + 1}

def should_replan(state):
    if state["current_step"] >= len(state["plan"]):
        return "end"
    return "executor"
```

### 怎么评估一个 Agent 系统的效果？

**答： **Agent 评估比普通 LLM 评估复杂得多，几个维度：

1. **任务完成率 **：最终是否完成了用户的目标
2. **步骤效率 **：用了多少步完成（越少越好）
3. **工具调用准确率 **：是否调用了正确的工具、传了正确的参数
4. **成本 **：总 token 消耗
5. **延迟 **：端到端响应时间

实操方法：

- 构建 benchmark 数据集（输入 + 期望输出 + 期望工具调用序列）
- 用 LangSmith 的 evaluation 功能跑批量测试
- LLM-as-judge：用另一个 LLM 评判 Agent 的输出质量

### LangSmith 是什么？跟直接部署有什么区别？

**答： **LangSmith 是官方的托管部署方案，提供：

- HTTP API 自动生成
- 后台任务队列（长时间运行的 Agent 不会超时）
- Cron 定时任务
- 内置 checkpointer（Postgres）
- 多租户支持
- 水平扩展

跟自己用 FastAPI 部署的区别：自己部署要自己处理长连接、状态持久化、任务队列这些基础设施。LangGraph Platform 帮你搞定了，但要付费。

如果团队小、流量不大，FastAPI + Redis + Postgres 自己搭也行。流量大了或者要快速上线，用 Platform 省心。

### LangChain 中的 LCEL 是什么？

LCEL：LangChain Expression Language；LangChain表达式语言。他是用来定义 一个 agent 流程的。这是早期语法。类似这样：

```plaintext
def some_func(x):
    return x

chain = some_func | runnable1
```

现在都是使用 create_agent() 创建 agent，所以这个废弃了。

### 什么是 LangGraph State（LangGraph 状态）

LangGraph State 是 LangGraph 框架中定义的在节点间共享数据的一个机制。

在 LangChain 框架中。这个 LangGraph State 就是我们说的短期记忆。通过 checkpointer 来指定短期记忆的存储方式，可以放到内存或者数据库等中间件中。

### 如何保存一个 LangGraph 状态？

通过给 agent 传递 checkpointer 对象（比如：InMemorySaver、PostgresSaver）

而且agent执行的时候，必须提供一个 thread_id，用来区分不用用户的 state（短期记忆）

### InMemorySaver 和 PostgresSaver 有什么区别？

InMemorySaver 把短期记忆数据保存到内存中。

PostgresSaver 把短期记忆数据保存到数据库中，即使意外中断、重启都可以恢复记忆

### 能不能给 记忆 中保存大文件？

不建议这样做。直接在状态中存储大文件会导致数据库膨胀，因为每一步都会保存一份新副本。正确的做法是将文件存储在 Minio 这类外部存储中，只在 LangGraph 状态里保存文件的 URL 即可。

### 什么时候用LangChain什么时候用LangGraph，有什么区别？

只是构建一个多轮对话，工具调用的智能体用LangChain。

如果我们是执行一个有明确流程的业务，就用 LangGraph 定义工作流。然后多轮对话都是执行整个工作流
