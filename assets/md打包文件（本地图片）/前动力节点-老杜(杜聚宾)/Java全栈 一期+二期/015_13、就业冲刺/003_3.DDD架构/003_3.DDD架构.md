# 3.DDD架构

# 一句话定义 DDD

领域驱动设计（DDD）是一种**以业务为核心**的软件设计方法论，核心思想：

- **让 代码结构 严格对齐 真实业务结构，用通用语言、明确边界、对象封装，去实现业务规则**。

# 三层架构与 DDD 的区别

## 对比

| **传统开发（三层架构）** | **DDD开发（业务驱动）** |
| --- | --- |
| 按技术分层：Controller → Service → DAO | 按业务边界拆分：订单域 / 商品域 / 用户域 / 支付域 |
| **技术优先**，业务迁就代码。 三层分层逻辑是按：请求怎么流转、数据怎么存进行切分的。因此我们把它叫做按技术分层。 | **业务优先**，用代码去**复刻**业务 |

DDD核心追求：**让不懂技术的业务人员，能看懂代码的业务划分与核心规则**。

## 三层架构中的业务划分与 DDD 架构中的业务划分

** 三层的 Service 划分 ≠ DDD 的业务划分，看着像，本质完全不一样！ **

### 三层架构是假业务划分

1. **三层是「按技术拆」，不是按「业务本质拆」**

传统三层： Controller（接请求）→ Service（堆逻辑）→ DAO（查库）

分多个 Service：OrderService、UserService、PayService。只是**文件名分开了**，内部还是：

- **实体是贫血 Bean**，只有 get/set，没业务规则
- 核心校验、状态判断**全散在 Service 里**
- 改一个业务规则，要搜全项目、改 N 个地方，业务分散，不集中。

1. **三层 Service 没「边界约束」**

传统 Service 随便互相注入： OrderService 能直接调 StockService、改库存、改支付

没有**限界上下文**，业务边界是虚的，全靠程序员自觉。人一懒，跨域逻辑乱堆，容易乱成一锅粥

1. **三层架构中业务和对象是割裂的**

传统：Order 实体类只是一张数据库表的映射，不会自己取消，自己支付。所有行为全靠外部 Service 指挥。

### DDD 架构是真业务划分

1. **先划领土（限界上下文）**
  1. 订单域只管订单，绝不插手库存 / 支付核心规则
  2. 跨域调用时禁止直接篡改。走**事件通知**或**开放接口**。
2. **把业务装进对象里**
  1. Order 自己能 cancel ()、pay ()，规则锁死在实体内部，不是 Service 到处 if else
3. **用分层来防污染**
  1. 领域层纯业务，不和数据库、框架挂钩
  2. 三层是围着数据库转，DDD 是围着业务转

### 什么是污染

以下代码就是被业务被技术污染了：

```java
// 被污染的领域对象
@Entity   // JPA框架污染
@Table(name="t_order") // 数据库表名污染
public class Order {
    @Id     // 主键注解污染
    private Long id;

    // 业务规则里还写Redis、MQ、SQL逻辑
    public void cancel(){
        redisTemplate.delete("order:"+id); // 缓存技术污染
        mqSender.send(xxx); // 消息技术污染
    }
}
```

业务被技术污染的后果是：

- 换数据库（MySQL→PG）、换框架（Spring→其他）、换中间件
- **你的核心业务规则（订单能不能取消）要跟着改！**
- 业务被技术绑死，这就是「技术污染业务」

### 什么是四层架构防污染

依靠 四层架构 画 **绝对隔离墙**：

- 把所有技术脏活，全赶到外层 / 底层；
- 核心业务关在「领域层」里，不许技术进来捣乱。

**分层隔离逻辑（防污染墙）**

1. **接口层**：只挡 HTTP 请求（技术）
2. **应用层**：只管流程、事务、调接口（轻技术）
3. ✅ **领域层：纯净土！只写业务，啥技术都不许碰**
4. **基础设施层**：包揽所有脏活（DB、Redis、MQ、Feign）

👉 这就叫：**用分层，把技术污染拦在外面，进不了核心业务**

### 领域层「不和数据库、框架挂钩」啥意思

**领域层严禁出现：**

- Spring 注解：`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">@Service</font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">@Component</font>`
- 数据库注解：`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">@Table</font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">@Id</font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">@Column</font>`
- 中间件：Redis、MQ、Feign、SQL
- 任何框架依赖

纯净领域对象（没被污染 ✅）

```java
// 纯Java，0框架、0DB、0中间件
public class Order {
    private Long id;
    private OrderStatus status;

    // 只有纯粹业务规则
    public void cancel(){
        if(status == 已支付) throw 异常;
        status = 已取消;
    }
}
```

这个类：

- 脱离 Spring 能运行
- 脱离 MySQL 能运行
- 脱离 Redis/MQ 照样能跑业务逻辑

**业务就是业务，跟用啥技术没关系**

# 为什么要用DDD？传统开发痛点

**传统三层架构**（贫血模型通病：**实体类中只有 get 和 set 方法，叫做贫血模型**）

```java
@Controller
public class OrderController { ... }

@Service
public class OrderService {
    // 下单/取消/支付/退款/改价全堆这里
    public void createOrder() { ... }
    public void cancelOrder() { ... }
    public void payOrder() { ... }
}

@Repository
public class OrderDao { ... }
```

**致命问题：**
❌ 所有业务逻辑堆砌在Service层，类动辄几千行
❌ 业务规则散落各处，校验重复、隐藏bug多
❌ 改一个功能牵连全局，上线风险极高
❌ 新人看不懂业务边界，**维护成本** 爆炸

# DDD标准目录结构

```plaintext
com/company/biz/
├── OrderApplication.java  // main启动类
├── order/                // 限界上下文：订单域
│   ├── interfaces/       // 接口层（对外HTTP/RPC）
│   │   └── OrderController.java
│   ├── application/      // 应用层（流程编排+事务），有@Service注解。
│   │   └── OrderAppService.java
│   ├── domain/           // 领域层（纯业务·无框架侵入），这是最核心的。
│   │   ├── model/        // 实体/值对象/聚合
│   │   │   ├── Order.java       // 聚合根·实体
│   │   │   ├── OrderItem.java   // 聚合内的 子实体
│   │   │   └── Money.java       // 值对象
│   │   ├── service/      // 领域服务（跨聚合复杂逻辑）
│   │   │   └── OrderCrossDomainService.java
│   │   └── repository/   // 仓储接口（无框架注解）
│   │       └── OrderRepository.java
│   └── infrastructure/   // 基础设施层（技术实现），有 @Repository 注解。
│       └── repository/impl/
│           └── OrderRepositoryImpl.java
```

1. 一个限界上下文对应一个微服务项目。
2. **domain 里的 Service、Repository**，和我们平时写的`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">@Service</font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">@Mapper</font>`完全不是一回事

**domain 里的「repository」**：是**接口 / 契约**，不是实现， 只放抽象接口，**没有任何 DB 代码、没有 MyBatis、没有 @Repository 注解**

```java
// domain/repository 领域层：纯抽象
public interface OrderRepository {
    Order findById(Long id);
    void save(Order order);
}
```

作用：解耦！业务只依赖「存取能力」，不依赖数据库技术， 真正的 SQL、实现，全丢到`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">infrastructure</font>`基础设施层去做。

**domain 里的「service」**：是**领域服务**，不是业务编排 Service

和普通 Service 的区别

- 平时`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">@Service</font>`（应用层）：管流程、事务、调外部接口
- domain/service（领域服务）：管**跨多个聚合、不属于任何单个实体**的核心业务规则比如：订单 + 优惠券 + 会员折扣，三个聚合一起算最终价 ——这个逻辑放单个 Order 里不合适，就抽成**领域服务**，放在 domain 里。

**特征**

1. 不加 Spring 注解
2. 只依赖领域实体、值对象
3. 只写核心业务规则，不碰 HTTP、MQ、DB

# DDD两大核心：战略设计 + 战术设计

DDD 架构包括两大核心：战略设计、战术设计。别想太多， 它就是故意起高大上名字吓唬人，本质就是：

- 大方向规划 = 战略
- 细节写代码 = 战术

## 战略设计（划边界）

### 限界上下文（Bounded Context）

定义：**独立的业务领地，领域名词、规则只在当前上下文生效，互不越界**。
举例（电商标准拆分）：

- 订单上下文：只负责下单、改单、取消、履约
- 商品上下文：只负责上架、下架、库存、规格
- 用户上下文：只负责注册、身份、权限、档案
- 支付上下文：只负责扣款、退款、对账、流水
通俗理解：像公司部门，财务不管发货，仓储不管定价。

### 通用语言（Ubiquitous Language）

弄一套通用的语言，让**开发**、**产品**、**业务专家**共用一套名词；**代码里的****类名、方法名，完全对齐业务话术****，杜绝技术黑话**。

## 战术设计（落地编码·造对象）

### ① 实体（Entity）

特征：**有唯一ID、生命周期可变、业务可追踪**；核心业务行为封装在自身内部。

```java
// 领域层·纯Java·无框架注解
public class Order {
    private Long id;
    private String orderNo;
    private OrderStatus status;
    private LocalDateTime cancelTime;

    // 业务行为，拒绝裸setter
    public void cancel() {
        if (OrderStatus.PAID.equals(this.status)) {
            throw new BusinessException("已支付订单不可取消");
        }
        if (OrderStatus.SHIPPED.equals(this.status)) {
            throw new BusinessException("已发货订单不可取消");
        }
        this.status = OrderStatus.CANCELLED;
        this.cancelTime = LocalDateTime.now();
        // 内置触发领域事件（事件发布交给应用层）
    }

}
```

### ② 值对象（Value Object）

特征：**无ID、不可变、纯描述属性；相等只看属性，不看地址**。

```java
public final class Money {
    private final BigDecimal amount;
    private final String currency;

    public Money add(Money other) {
        return new Money(this.amount.add(other.amount), this.currency);
    }
}
```

### ③ 聚合 & 聚合根（Aggregate / AggregateRoot）

- **聚合：**一组强关联、业务不可分的对象集群
- **聚合根：聚合唯一对外入口**；外部只能通过聚合根操作内部子对象，禁止直接修改子实体

```java
// Order是聚合根，OrderItem是内部子实体
public class Order {
    private List<OrderItem> itemList;

    // 只能由聚合根新增/修改子项
    public void addOrderItem(Product product, int num) {
        itemList.add(new OrderItem(product, num));
    }
}
```

### ④ 领域服务（Domain Service）

适用场景：**跨多个聚合根、无法归属到任意单一实体的复杂业务逻辑**。
错误用法：把单个订单的支付、取消塞进领域服务；
正确用法：订单+库存+支付三方联动扣减、分布式业务校验。

```java
// 领域层·无HTTP/DAO框架依赖
public class OrderSettleDomainService {
    // 订单、库存、支付多聚合协同
    public void settle(Order order, Stock stock, Payment payment) {
        // 跨域核心业务规则校验
    }
}
```

### ⑤ 仓储（Repository）

- **在领域层**：只定义**纯接口**，不加@Repository、@Mapper等任何框架注解
- **在基础设施层**：实现接口，对接数据库、MyBatis/JPA

```java
// 领域层：纯业务接口
public interface OrderRepository {
    Order findById(Long id);
    void save(Order order);
}

// 基础设施层：技术实现+框架注解
@Repository
public class OrderRepositoryImpl implements OrderRepository {
    // 封装DB CRUD、DO转换、缓存逻辑
}
```

# DDD标准四层架构

```plaintext
┌─────────────────────────────┐
│ 接口层 Interfaces            │
│ Controller / DTO / 路由     │ → 只收请求、返响应，无业务逻辑
├─────────────────────────────┤
│ 应用层 Application          │
│ AppService / 事务编排       │ → 流程串联、事务控制、调用领域、发布事件
├─────────────────────────────┤
│ 领域层 Domain（核心）       │
│ 实体/值对象/聚合/领域服务   │ → 纯业务、无框架、无DB依赖、核心规则全在这
│ 仓储接口、领域事件定义      │
├─────────────────────────────┤
│ 基础设施层 Infrastructure   │
│ 仓储实现 / MQ / 缓存 / DB   │ → 封装所有技术细节
└─────────────────────────────┘
```

**强制依赖规则**

1. 外层依赖内层，内层绝不依赖外层
2. 领域层完全纯净，不依赖Spring、MyBatis、MQ等任何技术框架
3. 所有技术细节，全部收口在基础设施层

# 传统贫血VS DDD充血

## 传统贫血写法

```java
@Service
public class OrderService {
    // 业务规则全散在Service，实体只有set/get
    public void cancel(Long orderId) {
        Order dbOrder = repo.selectById(orderId);
        if("PAID".equals(dbOrder.getStatus())){
            throw new Exception("不能取消");
        }
        dbOrder.setStatus("CANCEL");
        repo.update(dbOrder);
    }
}
```

## DDD充血标准写法

**第一步：领域实体封装业务规则**

```java
public class Order {
    public void cancel() {
        // 核心校验内聚在实体
        if (OrderStatus.PAID.equals(status)) {
            throw new BusinessException("已支付不可取消");
        }
        this.status = OrderStatus.CANCELLED;
    }
}
```

**第二步：应用层只做轻编排+事务**

```java
@Service
@Transactional
public class OrderAppService {
    private final OrderRepository orderRepo;
    private final PaymentRemote paymentRemote;

    // 极薄：只查数据、调领域、存数据、调外部
    public void cancelOrder(Long orderId) {
        Order order = orderRepo.findById(orderId);
        order.cancel(); // 业务规则全在领域
        orderRepo.save(order);
        paymentRemote.refund(orderId);
    }
}
```

# DDD 架构下的用户管理

DDD 做 CRUD 不是为了复杂， 是为了结构干净、业务纯净、不被技术污染。

1 个限界上下文（用户微服务）+ 标准 4 层 + 领域纯净。

## 领域层（最核心！纯业务，无任何框架注解）

**以下是聚合根，也就是业务本体**

```java
package com.example.user.domain.model;

/**
 * 领域实体 / 聚合根。 纯业务！！！
 * 没有 @Entity 没有 @Table 没有任何技术注解
 */
public class User {

    private Long id;
    private String username;
    private Integer age;

    // 业务规则：创建用户
    // 造对象的工厂方法是static的。
    // 所有对象自己干活的业务方法：全是普通实例方法（非 static）
    public static User create(String username, Integer age) {
        User user = new User();
        user.setUsername(username);
        user.setAge(age);
        return user;
    }

    // 业务规则：修改信息
    public void modifyInfo(String username, Integer age) {
        this.username = username;
        this.age = age;
    }

    // getter / setter
    public Long getId() {
        return id;
    }

    public void setId(Long id) {
        this.id = id;
    }

    public String getUsername() {
        return username;
    }

    public void setUsername(String username) {
        this.username = username;
    }

    public Integer getAge() {
        return age;
    }

    public void setAge(Integer age) {
        this.age = age;
    }
}
```

**以下是抽象契约：**

```java
package com.example.user.domain.repository;

import com.example.user.domain.model.User;

/**
 * 领域层定义接口：我要存、要查
 * 但我不管怎么存（MySQL/Redis都可以）
 */
public interface UserRepository {

    void save(User user);
```

## 应用层（流程编排，很薄）

```java
package com.example.user.application;

import com.example.user.domain.model.User;
import com.example.user.domain.repository.UserRepository;
import jakarta.annotation.Resource;
import org.springframework.stereotype.Service;

// 纯指挥官、纯流程编排；只管调度、事务、转发，绝不写核心业务规则
// 只干一件事：叫领域对象干活 → 叫仓储保存，自己不写任何业务规则！
@Service
public class UserAppService {

    // 注入的是领域接口，不是实现
    @Resource
    private UserRepository userRepository;

    // 查询
    public User getById(Long id) {
        return userRepository.getById(id);
    }

    // 新增
    public void create(String username, Integer age) {
        // 禁用直接 new，用静态工厂统一创建并内置业务校验，保证生成的领域对象从源头就合法合规
        // 在这里new，在这里set，又乱套了，不纯净。
        User user = User.create(username, age);
        userRepository.save(user);
    }

    // 修改
    public void update(Long id, String username, Integer age) {
        User user = userRepository.getById(id);
        user.modifyInfo(username, age);
        userRepository.update(user);
    }

    // 删除
    public void delete(Long id) {
        userRepository.delete(id);
    }
}
```

## 接口层（对外 API）

```java
package com.example.user.interfaces;

import com.example.user.application.UserAppService;
import com.example.user.domain.model.User;
import jakarta.annotation.Resource;
import org.springframework.web.bind.annotation.*;


@RestController
@RequestMapping("/user")
public class UserController {

    @Resource
    private UserAppService userAppService;

    @GetMapping("/{id}")
    public User get(@PathVariable Long id) {
        return userAppService.getById(id);
    }

    @PostMapping
    public void create(@RequestParam String username, @RequestParam Integer age) {
        userAppService.create(username, age);
    }

    @PutMapping("/{id}")
    public void update(@PathVariable Long id, @RequestParam String username, @RequestParam Integer age) {
        userAppService.update(id, username, age);
    }

    @DeleteMapping("/{id}")
    public void delete(@PathVariable Long id) {
        userAppService.delete(id);
    }
```

# 什么时候该用DDD？

**适合用**

- 业务复杂：电商、金融、支付、供应链
- 业务规则频繁变动、需要长期迭代维护
- 多团队协作，需要明确业务边界
- 有产品/业务专家参与梳理领域模型

**不适合用**

- 简单CRUD后台管理系统
- 纯报表、纯数据统计类项目
- 短期小项目、一次性需求
- 团队无能力梳理业务边界，只求快速上线

# 核心总结

1. DDD本质：**先理清业务边界，再用代码复刻业务，业务内聚到领域对象**
2. 三个关键抓手：
  - 战略：限界上下文划清业务地盘
  - 战术：实体/值对象/聚合封装业务
  - 架构：四层分层+单向依赖，保证领域纯净
3. 终极口诀：**业务语言即代码语言，业务规则全在领域，技术细节全在底层**
