# 2.2.并发编程面试题

# 什么是线程安全？如何实现线程安全？

**线程安全就是：**多线程同时并发访问一个共享的数据，并且对数据进行了修改操作，但不出问题。

**实现线程安全有三种方式：**

**第一，互斥同步**，也就是加锁，用 `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">synchronized</font>` 或者 `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">ReentrantLock</font>`，让同一时刻只有一个线程执行。

**第二，非阻塞同步**，基于CAS，比如 `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">AtomicInteger</font>`，线程不会阻塞，失败就重试，性能比锁好。

**第三，不共享**，用 `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">ThreadLocal</font>` 给每个线程一份自己的副本，或者用局部变量、不可变对象，这样压根就没有竞争。

# 什么是 CAS（Compare And Swap）？

**是无锁原子操作：**

1. 先拿**预期旧值**和内存里的值对比
2. 相等 → 直接更新成新值
3. 不相等 → 修改失败，重试（**自旋**）

**CAS 是一种 CPU 层面的原子操作思想，几乎所有现代 CPU 都直接支持，Java 只是通过 **`<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">Unsafe</font>`** 类把它封装成了开发者可用的 API。**

| **层面** | **说明** |
| --- | --- |
| **CPU 层面** | CAS 是一条 CPU 汇编指令（如 x86 的 `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">cmpxchg</font>`），由硬件保证原子性，跟编程语言无关。 |
| **操作系统层面** | 系统库会封装 CPU 的 CAS 指令，供上层语言调用。 |
| **Java 层面** | `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">sun.misc.Unsafe</font>`类通过 JNI 调用操作系统的 CAS 实现，`<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">AtomicInteger</font>`等类再封装 `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">Unsafe</font>`。 |

**多线程并发的环境下，如果多线程共享同一个计数器，不要直接使用 `**count++**`，他是非线程安全的，可以使用 **`**AtomicInteger**`**类，它可以实现计数器功能，并且是线程安全的。**

---

**示例代码：**

```java
import java.util.concurrent.atomic.AtomicInteger;

public class Counter {
    private AtomicInteger count = new AtomicInteger(0);
    
    // 线程安全的 +1
    public void increment() {
        count.incrementAndGet();  // ++i，返回新值
        // 或者 count.getAndIncrement();  // i++，返回旧值
    }
    
    // 线程安全的 +n
    public void add(int n) {
        count.addAndGet(n);  // 加n，返回新值
    }
    
    // 获取当前值
    public int get() {
        return count.get();
    }
}
```

# 什么是自旋？自旋和互斥锁的区别？

**自旋就是：**CAS 失败立刻重试，**线程全程不停止、不休息，一直占着 CPU 死循环**。之所以叫**不阻塞**，是线程一直处于运行状态，没被操作系统挂起、没放弃 CPU。**优点：**响应快，没有线程上下文切换开销；**缺点：**一直空转啃 CPU，并发一高，CPU 直接跑满。

**synchronized 是典型互斥锁**：抢锁失败直接**躺平休眠、进入阻塞队列，主动让出 CPU**。优点：不浪费 CPU 资源；缺点：要走内核态切换、唤醒线程，上下文切换开销大，延迟高。

**自旋 = 忙等，耗 CPU 不耗切换；**

**互斥阻塞 = 闲等，省 CPU 但耗切换成本。**

# AtomicInteger和LongAdder有什么区别？

AtomicInteger 是 JDK1.5 提供、基于单变量 volatile 值 + CAS 无限自旋实现的原子类，适合低并发少量竞争场景，支持 compareAndSet 等复杂 CAS 操作，能实现判断再修改的业务逻辑，可用于订单序号、ID 自增等场景；

LongAdder 是 JDK1.8 推出的，采用分段累加思想，将数值拆分为基础值 base 和 Cell 分段数组，低并发修改 base、高并发把线程分散到不同 Cell 单独累加，最终汇总 base 与所有 Cell 的值，大幅减少 CAS 竞争与自旋次数，高并发下吞吐量更高、CPU 占用更低，但它仅支持纯累加计数，不支持自定义 CAS 比较交换，只适用于接口 QPS 统计、流量打点等高并发统计场景。

简单来说 AtomicInteger 功能全面但高并发竞争激烈耗 CPU，LongAdder 专攻高并发纯计数、性能极强却无法实现复杂 CAS 业务判断。

**怎么理解 LongAdder 的实现原理？**

**LongAdder 被拆分为两部分：**

- **base：基础值**并发不大时，大家直接偷偷改 base，跟 AtomicInteger 一样，简单快。
- **Cell [] 单元格数组（核心！）**搞一个数组，里面每一个位置都是一个独立变量（Cell）

**高并发时，Cell 是怎么干活的？**

1. 线程来了，先试着改 base；
2. 发现抢 base 的人太多、CAS 失败 → 直接**分流**；
3. 根据当前线程的哈希值，给这个线程分配一个专属 Cell 格子；
4. 线程只给自己分到的那个 Cell 做累加，**互不打扰、不抢、不冲突**，几乎不需要自旋。

**最终总数怎么算？**

调用 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">sum()</font>` 拿总数：**总数值 = base + 把所有 Cell 里的值全部累加一遍**

平时计数各自记，最后汇总求和就行

# 什么是死锁？如何避免死锁？

**什么是死锁？**

两个线程互相持有对方需要的锁，谁也不释放，导致都卡住。比如A拿锁1等锁2，B拿锁2等锁1。

**如何避免？**

最常用的方法是**给锁编号，所有线程按固定顺序加锁**，破坏循环等待。另外也可以用 `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">tryLock</font>` 设置超时，拿不到就释放已有锁。

## 给锁编号

线程 1 获取锁的顺序是：先获取锁 1，再获取锁 2

线程 2 获取锁的顺序也是：先获取锁 1，再获取锁 2

这样就不会死锁了，例如以下代码：

```java
// 定义锁，带上编号
Object lock1 = new Object();  // 编号1
Object lock2 = new Object();  // 编号2

// 规则：必须先拿编号小的锁（1），再拿编号大的锁（2）

// 线程A
synchronized(lock1) {  // 先拿1 ✓
    synchronized(lock2) {  // 再拿2 ✓
        // 业务代码
    }
}

// 线程B
synchronized(lock1) {  // 也是先拿1 ✓
    synchronized(lock2) {  // 再拿2 ✓
        // 业务代码
    }
}
```

## tryLock

**tryLock 尝试获取锁，如果锁被别人占着，不会傻等，而是立即返回 false，这样就避免死锁了。**

```java
import java.util.concurrent.locks.ReentrantLock;

public class TryLockDemo {
    private static ReentrantLock lock1 = new ReentrantLock();
    private static ReentrantLock lock2 = new ReentrantLock();

    public static void main(String[] args) {
        Thread t1 = new Thread(() -> {
            while (true) {
                if (lock1.tryLock()) {        // 尝试拿锁1
                    try {
                        if (lock2.tryLock()) { // 尝试拿锁2
                            try {
                                System.out.println("线程1拿到了两把锁");
                                break;
                            } finally {
                                lock2.unlock();
                            }
                        }
                    } finally {
                        lock1.unlock();
                    }
                }
                // 没拿到就等一下再重试
                try { Thread.sleep(10); } catch (InterruptedException e) {}
            }
        });


        Thread t2 = new Thread(() -> {
            while (true) {
                if (lock2.tryLock()) {        // 尝试拿锁2
                    try {
                        if (lock1.tryLock()) { // 尝试拿锁1
                            try {
                                System.out.println("线程2拿到了两把锁");
                                break;
                            } finally {
                                lock1.unlock();
                            }
                        }
                    } finally {
                        lock2.unlock();
                    }
                }
                try { Thread.sleep(10); } catch (InterruptedException e) {}
            }
        });

        t1.start();
        t2.start();
    }
}
```

# Java中如何创建线程？

**Java中创建线程有四种方式：继承Thread类、实现Runnable接口、实现Callable接口、使用线程池。**

| **方式** | **代码示例** | **特点** |
| --- | --- | --- |
| **1. 继承Thread** | `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">new MyThread().start()</font>` | 简单，但Java单继承，不能再继承其他类 |
| **2. 实现Runnable** | `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">new Thread(() -> {}).start()</font>` | 推荐，更灵活，可以再继承其他类 |
| **3. 实现Callable** | `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">FutureTask + Thread</font>` | 可以有返回值，能抛异常 |
| **4. 线程池** | `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">Executors.newFixedThreadPool(10)</font>` | 最佳实践，减少线程创建销毁开销 |

# 线程池的七大参数是什么？

**这七大参数是 JDK 内置的 **`**<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">ThreadPoolExecutor</font>**`** 类的构造方法参数，是 Java 原生提供的。**

**线程池的七大参数是：核心线程数、最大线程数、空闲存活时间、时间单位、阻塞队列、线程工厂、拒绝策略。**

| **参数** | **构造方法中的顺序** | **作用** |
| --- | --- | --- |
| **1. corePoolSize** | 第1个 | 核心线程数，一直存活（除非设置allowCoreThreadTimeOut） |
| **2. maximumPoolSize** | 第2个 | 最大线程数，忙的时候最多能扩到这么多 |
| **3. keepAliveTime** | 第3个 | 空闲线程存活时间，超过这个时间没活干就销毁 |
| **4. unit** | 第4个 | 存活时间的单位（秒、毫秒等） |
| **5. workQueue** | 第5个 | 阻塞队列，存放等待执行的任务 |
| **6. threadFactory** | 第6个 | 线程工厂，用来创建线程（可以自定义名称） |
| **7. handler** | 第7个 | 拒绝策略，队列和线程池都满了时的处理方式 |

# 线程池的工作流程是怎样的？

```plaintext
提交任务
    ↓
① 核心线程满了吗？→否  创建新线程执行任务（完成）
    ↓ 是
② 队列满了吗？→ 否  任务放入队列，等空闲线程来取（完成）
    ↓ 是
③ 最大线程满了吗？→ 否  创建新临时线程执行任务（完成）
    ↓ 是
④ 触发拒绝策略
```

# 项目中线程池的线程数你是怎么设置的？

**配置线程池参数，核心是根据任务类型来定：**

**如果是CPU密集型任务**（比如大量计算），线程数设为 `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">CPU核心数 + 1</font>`，因为线程多了反而会增加上下文切换开销。

**如果是IO密集型任务**（比如数据库查询、HTTP调用），线程数可以设大一点，比如 `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">CPU核心数 × 2</font>`，因为大部分时间线程在等待IO，CPU是空闲的。

**队列建议用有界队列（有固定容量的队列）**，防止任务堆积导致内存溢出。拒绝策略推荐用 `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">CallerRunsPolicy</font>`，让调用者线程自己执行，起到降级缓冲的作用。

**如果任务类型差异很大**，建议拆分成多个线程池，分别配置，避免互相影响。

**为什么 CPU 核心数+1？因为当线程偶尔发生阻塞时，+1这个线程可以顶上，充分利用CPU时间。**

# 线程池的拒绝策略有哪些？

**线程池有四种拒绝策略：AbortPolicy、CallerRunsPolicy、DiscardPolicy、DiscardOldestPolicy。**

| **策略** | **行为** | **特点** |
| --- | --- | --- |
| **AbortPolicy** | 直接抛异常 `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">RejectedExecutionException</font>` | **默认策略**，让上层感知问题 |
| **CallerRunsPolicy** | 让**调用者线程**自己执行任务 | 起到降级缓冲作用，不会丢任务 |
| **DiscardPolicy** | 直接丢弃任务，啥也不干 | 可能丢失任务，适合不重要的场景 |
| **DiscardOldestPolicy** | 丢弃队列里**最老**的任务，再提交当前任务 | 追求最新数据，适合消息场景 |

# 核心线程能否被回收？

**默认情况下，核心线程不会被回收，会一直存活。**

**但是，可以通过**** **`**<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">allowCoreThreadTimeOut(true)</font>**`** 方法来改变这个行为。设置之后，核心线程空闲时间超过 **`**<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">keepAliveTime</font>**`** ****也会被回收，线程数可以降到0。**

**这个功能一般用在线程池需要动态缩容的场景，比如业务低峰期释放资源。**

**什么是核心线程？如果你只设置了一个数字（比如用 **`**<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">Executors.newFixedThreadPool(10)</font>**`**），那10个都是核心线程。但如果你用的是 **`**<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">ThreadPoolExecutor</font>**`** 的7参构造，核心线程数和最大线程数可以分开设置。**

| **创建方式** | **核心线程数** | **最大线程数** | **10个都是核心吗？** |
| --- | --- | --- | --- |
| `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">Executors.newFixedThreadPool(10)</font>` | 10 | 10 | ✅ 是，全是核心 |
| `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">new ThreadPoolExecutor(10, 10, ...)</font>` | 10 | 10 | ✅ 是，全是核心 |
| `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">new ThreadPoolExecutor(5, 10, ...)</font>` | 5 | 10 | ❌ 不是，5个核心 + 最多5个临时 |

# 如何监控线程池状态？

**通过 **`**<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">ThreadPoolExecutor</font>**`** 提供的监控方法，可以获取线程池的核心指标，如活跃线程数、任务数、队列大小等。**

| **方法** | **返回值** | **含义** |
| --- | --- | --- |
| `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">getPoolSize()</font>` | int | 当前线程池中的线程总数（核心+临时） |
| `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">getActiveCount()</font>` | int | 正在执行任务的线程数 |
| `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">getCorePoolSize()</font>` | int | 核心线程数 |
| `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">getMaximumPoolSize()</font>` | int | 最大线程数 |
| `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">getQueue().size()</font>` | int | 队列中等待的任务数 |
| `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">getTaskCount()</font>` | long | 历史累计提交的任务总数 |
| `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">getCompletedTaskCount()</font>` | long | 已完成的任务数 |
| `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">getLargestPoolSize()</font>` | int | 历史最高峰时的线程数 |

**直接背这段话：**

**监控线程池状态，主要有两个层面：**

**第一，利用**** **`**<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">ThreadPoolExecutor</font>**`** ****自带的方法**，比如 `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">getActiveCount()</font>` 看活跃线程数，`<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">getQueue().size()</font>` 看排队任务数，`<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">getCompletedTaskCount()</font>` 看完成任务数。这些方法可以随时获取线程池的快照状态。

**第二，生产环境需要持续监控**，可以用一个定时任务每隔几秒打印这些指标，或者上报到 Prometheus、Grafana 等监控系统。当队列积压超过阈值时发送告警，及时发现线程池瓶颈。

# ThreadLocal原理？为什么会内存泄漏？

1. 放在 ThreadLocal 当中的数据是线程安全的，这个数据是当前线程独享的。
2. ThreadLocal 底层原理是：
  1. 每个线程内部都会有一个自己专属 ThreadLocalMap 对象，每个线程都不一样。
  2. ThreadLocalMap 的 key 存储的是 ThreadLocal 对象的引用，value 是的绑定的数据。
3. 把 ThreadLocal 对象比作钥匙，这把钥匙全局共享一个。
4. 把 ThreadLocalMap 对象比对每个线程自己私有的小抽屉。
5. 线程自己私有的小抽屉中可以存放多个 key-value，怎么实现呢？创建多个 ThreadLocal 即可。
6. 一个 ThreadLocal → 一条数据；多个 ThreadLocal → 多条数据；

**强引用、弱引用、软引用分别是什么？**

- **强引用（默认）**：`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">Object a = new Object();</font>` 不手动置空，GC 绝不回收
- **弱引用 WeakReference**：遇 GC 必收，**Java 为了防止 ThreadLocal 对象本身的内存泄漏问题，将 ThreadLocal 对象包装成了弱引用对象。**
- **软引用 SoftReference**：内存够就留，内存不够再收

**回答第二个问题：为什么会内存泄漏？**

**Java 为防止 ThreadLocal 对象自身内存泄漏，把 ThreadLocal 包装成弱引用当作 ThreadLocalMap 的 key；当外部切断 ThreadLocal 的强引用后，GC 会回收这个弱引用 key，让 Map 里的 key 变成 null。但 JVM 只会回收 key 对象，不会自动删除 Map 中整条键值对，value 依旧被强引用驻留；再加上线程池核心线程长期不销毁，残留的 value 一直无法释放，最终造成内存泄漏。所以使用完 ThreadLocal，必须手动调用 remove() 清除 key 和 value，彻底规避内存泄漏，同时避免线程复用带来的脏数据问题。**

# 如何设计一个分布式ID生成器？

**可以使用雪花算法。**

---

**标准雪花算法结构（64 位 Long）**

- 1 位符号位固定 0 +
- 41 位时间戳（毫秒级，可用几十年）+
- 10 位机器ID（区分不同服务节点）+
- 12 位序列号（同一毫秒内自增，支撑并发）

优点：本地生成、无 RPC、趋势递增、数据库索引友好。

**使用雪花算法生成分布式 ID 需要解决一些问题：**

- 机器 ID 重复：用 Redis 分配唯一 workerId；
- 时钟回拨（严重 bug）：记录最后时间戳，回拨直接报错 / 等待 / 兜底；
- 毫秒并发打满：自旋等待下一毫秒。【打满是指： 同一毫秒、同一机器：最多能生成 **4096 个 ID（0~4095），这 4096 个序号全用完了 **】

# volatile关键字有什么作用？能保证原子性吗？

## CPU 缓存与主内存

**CPU 缓存 **= CPU 自己带高速缓存（L1/L2/L3 Cache）, 就在 CPU 核子里，速度极快 。

**主内存 = 机器内存条（RAM）,公共大仓库。 所有数据最终存在这**，慢，但空间大 。

---

**为什么非要分两层？**

- **CPU 运算贼快（纳秒级）, 内存条（主内存）很慢（慢几百倍）, 如果 CPU 每次算东西都直接读 / 写内存条， CPU 会被卡死，全程等内存，CPU 利用率太低。**

## volatile 关键字有什么作用

1. **保证可见性**

多线程环境下：

- 普通变量：线程会缓存到自己工作内存（CPU 缓存），改了别的线程看不见；
- **volatile 修饰变量：强制读写主内存**，一个线程修改，其他线程立刻能看到最新值。

1. **禁止指令重排**

JVM/CPU 为优化性能会打乱代码执行顺序；

volatile 加**内存屏障**，阻止乱序执行，单例模式的 DCL 双重检查锁必须加 volatile，防止对象半初始化泄漏。

## 再次理解一下指令重排

CPU / 编译器为了**跑更快**，会把代码**打乱顺序执行，单线程还好，多线程并发的时候就麻烦了。**

```java
public class Singleton {
    private static Singleton instance;

    private Singleton(){}

    public static Singleton getInstance(){
        if (instance == null) {   // 第一次检查
            synchronized (Singleton.class){
                if (instance == null){ // 第二次检查
                    instance = new Singleton(); // 坑在这里！
                }
            }
        }
        return instance;
    }
}
```

**new Singleton() 真实分 3 步：**

1. 开辟内存空间
2. 初始化对象（赋值成员变量、构造方法）
3. 把 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">instance</font>` 引用指向这块内存

**CPU 会重排序！变成：**

1. 开辟内存
2. 先把 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">instance</font>` 指向内存（赋值引用）
3. 再慢慢初始化对象

如果不禁止指令重排序，最终结果是：instance 不为 null，但对象还没构造完 —— 拿到一个半成品、残次品对象。

## volatile 能保证原子性吗

**不能！**比如：`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">i++</font>`

- 分三步：读取→自增→写回
- volatile 只能保证「读、写立马可见」
- 没法把三步合成一个不可拆分的原子操作；多线程下照样会覆盖、数据错乱。

**要原子性**：用 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">synchronized</font>` / `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">ReentrantLock</font>` / `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">AtomicInteger</font>`。

# 如何保证库存扣减不超卖？

我在代驾系统中做过类似的业务，**司机抢单防超抢、防多人同时抢到同一订单**，核心用的就是 **Redis + Lua 脚本** 实现。

**为什么用 Redis+Lua**

Redis 执行 Lua 脚本是**单线程原子执行**，不会被并发打断；我把两个核心操作塞进同一个 Lua 脚本：

1. 判断：当前订单是不是**未被抢走**
2. 占单：校验通过，立刻把订单标记为**已被当前司机抢占**

两步合成一个不可拆分的原子操作，杜绝多人同时抢到同一单。

**Lua 核心逻辑**

脚本里先查订单抢占标识：

- 如果订单已经被抢 → 直接返回抢单失败
- 如果订单没人抢 → 立刻绑定司机 ID、修改订单抢占状态，原子完成占单

保证：**同一订单，只会有一个司机抢单成功**，剩下所有司机全部拦截。

**为什么不用别的？**

1. 本地锁 synchronized：微服务多实例，完全拦不住分布式并发
2. 普通 Redis get/set 分开写：中间有间隙，依然会并发抢单
3. 分布式锁：太重、性能差，抢单高并发场景不适合

Redis+Lua 轻量、吞吐高、延迟低，特别贴合代驾抢单这种瞬时高并发场景。

# 从不同的维度来看，锁是如何分类的？

| **维度** | **分类1** | **分类2** | **解释** |
| --- | --- | --- | --- |
| **公平性** | 公平锁 | 非公平锁 | **公平锁：**线程获取锁的**顺序**与请求锁的**时间顺序**完全一致（FIFO，先进先出） **非公平锁：**线程获取锁的**顺序**与请求锁的**时间顺序没有必然关系** |
| **共享性** | 共享锁 | 排他锁（独占锁） | **共享锁：**同一时刻**允许多个线程**同时持有该锁 **排它锁：**同一时刻**只允许一个线程**持有该锁 |
| **并发态度** | 悲观锁 | 乐观锁 | **悲观锁：**一上来先把数据锁住，然后我自己再修改。 **乐观锁：**一上来不加锁，先试试看，不行重试。 |
| **阻塞行为** | 阻塞锁 | 非阻塞锁（如自旋锁、CAS） | **线程在获取锁失败时的行为。** **阻塞锁：**线程**停下来等待**（被挂起，释放CPU），直到锁可用 **非阻塞锁**：线程**不停下来**（要么立即返回失败，要么继续尝试【自旋】） |
| **可重入性** | 可重入锁 | 不可重入锁 | **可重入锁：允许同一个线程未释放锁时再次获取锁（仅增加计数）** **不可重入锁：不允许，否则会死锁。** |
| **可中断性** | 可中断锁 | 不可中断锁 | **可中断锁**：线程在等待锁的过程中，其他线程给它发了`<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">Thread.interrupt()</font>`中断信号后，自动中断。不会继续傻等。 **不可中断锁**：线程在等待锁的过程中，**无视**中断信号。即使其他线程调用了它的`<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">interrupt()</font>`，它依然会继续等待锁，直到真正拿到锁为止 |
| **超时支持** | 支持超时的锁 | 不支持超时的锁 | **支持超时的锁**：尝试获取锁时，可以指定一个**最长等待时间**。如果在时间内没拿到锁，就主动放弃，不再傻等。 **不支持超时的锁**：尝试获取锁时，要么立刻成功/失败（不等待），要么**无限等待**下去，直到拿到锁为止。 |

`**synchronized**`**属于什么锁？**

- **非公平、排他、悲观、可重入、不可中断、无超时**

**通过下面这个代码理解一下可重入：**

```java
public synchronized void methodA() {
    // 获得锁
    methodB(); // 直接进入，不会死锁
}
public synchronized void methodB() {
    // 同一个线程再次获得同一把锁
}
```

# synchronized 在 JDK1.6 之后做了哪些优化？

JDK1.6 之前，**只要线程遇到 **`**<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">synchronized</font>**`** 关键字，JVM 就会立刻向操作系统申请互斥量（mutex），直接进入重量级锁。**

**互斥量就是操作系统提供的一个“门禁卡”：同一时间只能发给一个人，其他人必须排队等着，并且领卡、还卡都要找操作系统内核办理，所以很慢。**

**重量级锁的核心就是：等待-唤醒机制，并且每次交互都要经过用户态和内核态的切换。程序平时在用户态运行，需要干特权操作（比如申请锁、读写文件）时，必须找内核态帮忙，这就叫“切换”。这个切换是重量级的。**

**JDK1.6 之后做了如下优化：**

**1. 锁升级机制**

引入了**无锁 → 偏向锁 → 轻量级锁 → 重量级锁**的锁升级过程。锁会根据竞争激烈程度**单向自动升级**，竞争不激烈时使用轻量级锁，避免直接进入重量级锁。

**2. 偏向锁**

当只有一个线程反复获取锁时，JVM 会将对象头标记为偏向锁，记录该线程的 ID（**线程ID直接存储在对象头的Mark Word 当中**）。这个线程再来时**无需任何同步操作**，直接进入，开销几乎为零。

**3. 轻量级锁**

当有少量线程轻度竞争时，锁升级为轻量级锁。线程通过 **CAS 自旋**尝试获取锁，**不阻塞线程**，避免了**用户态到内核态的切换**开销。

**4. 自适应自旋**

轻量级锁的自旋不是固定次数，而是**根据上次自旋是否成功**动态调整。上次成功了就多自旋一会儿，失败了就少自旋或快速升级为重量级锁。

**5. 锁消除**

JVM 通过**逃逸分析**，发现某个锁对象只存在于当前线程的栈帧中，不可能被其他线程访问时，会**自动去掉这个锁**，消除无意义的同步。

```java
public void method() {
    // 逃逸分析：lock 对象只在当前方法内有效，不可能多线程共享
    Object lock = new Object();  
    synchronized(lock) { // 锁消除
        // 操作
    }
}
```

**6. 锁粗化**

当 JVM 检测到连续的加锁、解锁操作（比如循环内的 `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">synchronized</font>`），会将**多个锁操作合并成一个**，减少加锁解锁的次数，降低性能开销。

通过这些优化，`<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">synchronized</font>` 在大多数场景下性能已经不亚于 `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">ReentrantLock</font>`，JDK 官方也推荐优先使用 `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">synchronized</font>`。

# synchronized和ReentrantLock有什么区别？

**一句话总结**

`synchronized` 是JVM层面的内置锁，使用简单、自动释放；`ReentrantLock` 是API层面的显式锁，功能更丰富、灵活可控。

**详细区别**

1. **底层实现**

- **synchronized**：JVM 关键字，底层依赖 `monitorenter` / `monitorexit` 指令，锁的获取与释放由JVM自动完成。
- **ReentrantLock**：Java 类（`java.util.concurrent.locks.ReentrantLock`），依赖 AQS（AbstractQueuedSynchronizer），由代码控制加锁与解锁。

1. **锁的释放**

- **synchronized**：自动释放（异常或代码块结束），不会忘记，避免死锁。
- **ReentrantLock**：必须在 `finally` 块中手动 `unlock()`，否则极易造成死锁。

1. **灵活性**

| **功能** | **synchronized** | **ReentrantLock** |
| --- | --- | --- |
| 非阻塞获取锁 | ❌ 不支持 | ✅ `tryLock()` |
| 支持超时 | ❌ 不支持 | ✅ `tryLock(timeout, unit)` |
| 支持中断 | ❌ 不支持interrupt() 中断 | ✅ `lockInterruptibly()` |
| 公平锁 | ❌ 不支持，只支持非公平 | ✅ 构造参数可指定公平/非公平 |
| 多条件变量 | ❌ 只有一个等待队列 | ✅ 多个 `Condition`（可精准唤醒线程） |

**性能**

- 早期 `synchronized` 性能差，但JDK 1.6后引入了**偏向锁、轻量级锁、锁粗化、锁消除**等优化，两者性能差距已很小。
- 在高竞争场景下，`ReentrantLock` 通常仍略优（因为它的调度更灵活）。

**锁的获取方式**

- **synchronized**：隐式获取，代码更简洁。
- **ReentrantLock**：显式调用 `lock()` / `unlock()`，代码稍繁琐但可控性强。

**锁的调试**

- **synchronized**：JVM 诊断工具（如 `jstack`）可以明确显示锁信息。
- **ReentrantLock**：因为是普通Java对象，某些工具中识别不如 `synchronized` 直观。

**按照下面的背：**

**我认为两者的核心区别在于：**

- `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">synchronized</font>` 是 JVM 层面的关键字，锁的获取与释放由 JVM 自动完成，使用简单、不易出错；
- 而 `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">ReentrantLock</font>` 是 API 层面的锁，需要手动加锁和解锁，通常放在 `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">finally</font>` 块中。

**从功能上看：**

- `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">ReentrantLock</font>` 更加灵活，支持 **非阻塞的 **`**<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">tryLock()</font>**`、**带超时支持**、**可中断支持**，以及**公平锁**和**多个 **`**<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">Condition</font>**`** 等待队列**。（`**<font style="color:#DF2A3F;background-color:rgb(235, 238, 242);">ReentrantLock</font>**`**是一个 **`**<font style="color:#DF2A3F;">Condition</font>**`**条件对象对应一个等待队列，一个等待队列中存放了等待该条件成立的线程。**）
- 而 `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">synchronized</font>` 在这些方面都不支持，只有一个等待队列，要唤醒就把所有线程全部唤醒了，不精准。

**性能方面：**

- 早期 `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">synchronized</font>` 较差，但 JDK 1.6 之后引入了偏向锁、轻量级锁等优化，两者性能差距已经很小。所以在实际开发中，我会优先使用 `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">synchronized</font>`，代码更简洁、更安全；
- 只有当需要高级特性（比如实现一个阻塞队列需要区分‘非空’和‘未满’两个条件时），才会选择 `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">ReentrantLock</font>`。

# ConcurrentHashMap如何保证线程安全？1.7和1.8区别？

**JDK 1.7：分段锁（ReentrantLock）**
**JDK 1.8+：CAS + synchronized**

**JDK 1.7 版本**：采用 **Segment + HashEntry** 的结构。一个 ConcurrentHashMap 包含多个 Segment，每个 Segment 继承 ReentrantLock，相当于一个**小型的 HashMap**。写操作只锁住对应的 Segment，不同 Segment 之间可以并发写入。默认有 16 个 Segment，理论支持 16 个线程并发写入。

```plaintext
ConcurrentHashMap (JDK 1.7)
    │
    └── Segment[] 
         │
         └── Segment (继承 ReentrantLock，所以它本身就是一把锁)
              │
              └── HashEntry[] (数组，类似 HashMap 的 table)
                   │
                   └── HashEntry (节点) → HashEntry (next) → ... 链表
```

**JDK 1.8 版本**：取消了 Segment，改用 **Node 数组 + CAS + synchronized** 实现。锁的粒度从“段”细化为**单个数组桶（即链表或红黑树的头结点）**。put 时，如果对应桶为空，用 CAS 插入；如果有冲突，用 `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">synchronized</font>` 锁住桶的头结点，保证线程安全。同时引入了红黑树，当链表长度超过 8 且数组长度超过 64 时，链表转为红黑树，优化查询性能。

**JDK1.8 中为什么要使用 CAS？**

CAS 是一种**无锁**的线程安全方案，在**冲突极低**的场景下，比加锁性能好得多。HashMap 通常比较稀疏，**桶为空的概率很高。**CAS 失败后，再走 synchronized 也不迟。但需要注意的是：**CAS 只在桶为空、放第一个元素时使用。一旦桶里有了节点（不管是一个还是多个），后续操作全部走 synchronized 锁头结点。**

两者的核心区别可以总结为：**1.7 是“分段锁”，1.8 是“桶锁 + CAS”，锁粒度更细，并发度更高，并且利用了 synchronized 在 JDK 1.6 后的性能优化，不再依赖 ReentrantLock。**

# CopyOnWriteArrayList的原理和适用场景？

## 核心原理（说清楚“写时复制”）

**详细展开：**

1. **数据结构**：内部用一个 `volatile transient Object[] array` 存储元素。
2. **读操作**（如 `get(int index)`）：
  - 直接访问当前数组，**无锁**，非常快。
  - 不保证实时一致性（弱一致性），但保证最终一致性。
3. **写操作**（如 `add(E e)`）：
  - 先加 `ReentrantLock` 锁（或早期版本用 `synchronized`）。
  - 复制当前数组 → 长度+1 → 在新数组上添加元素 → 将新数组赋值给 `array`（volatile 写，保证可见性）。
  - 释放锁。
4. **迭代器**：
  - 创建迭代器时，拿到当前数组的一个快照（引用）。
  - 迭代过程中，其他线程对原 List 的修改不影响这个迭代器（**不会抛出 **`ConcurrentModificationException`）。

## 适用场景（强调“读多写极少”）

适合以下**两个条件同时满足**的场景：

1. **读操作远远多于写操作**
  - 因为读无锁，写要复制整个数组（开销很大）。
2. **数据量较小**
  - 写操作复制数组时，如果数组很大，会频繁发生 GC 和内存复制。

**典型例子**：

- **配置/规则列表**：系统启动后加载，偶尔修改（例如黑名单、白名单）。
- **事件监听器列表**：注册/注销监听器是低频操作，遍历通知是高频。
- **缓存中的只读数据集合**。

## 不适合的场景

| **场景** | **原因** |
| --- | --- |
| **写操作频繁** | 每次写都复制整个数组，性能差、GC 压力大 |
| **实时一致性要求高** | 读可能读到旧数据（写还未完成时） |
| **数据量很大** | 复制成本太高，可能导致 STW（Stop-The-World） |

## 与 `Collections.synchronizedList` 对比

| **特性** | **CopyOnWriteArrayList** | **synchronizedList** |
| --- | --- | --- |
| 读性能 | 极高（无锁） | 一般（需竞争锁） |
| 写性能 | 差（复制数组） | 好（仅加锁） |
| 迭代器 | 快照，不改不抛异常 | 修改时可能抛异常 |
| 一致性 | 弱一致性 | 若迭代器未同步，也弱一致性 |

## 面试回答示例（背诵）

**“CopyOnWriteArrayList 的核心原理是写时复制。写操作先加锁，然后复制一份新数组，在新数组上完成修改，最后把原数组引用指向新数组。读操作直接在原数组上无锁访问，因此读性能极高，迭代器基于快照，不会抛出 ConcurrentModificationException。”**

**“它最适合读多写极少、数据量小的场景，比如监听器列表、配置信息列表等。但如果写操作频繁或数据量很大，复制数组的开销会成为性能瓶颈，这时应该考虑普通的 ArrayList 加手动锁或 ConcurrentLinkedQueue 等。”**

# 如何设计一个秒杀系统？

## 什么是秒杀系统

海量请求一瞬间涌进来，商品库存极少（比如 10 台手机、100 张优惠券）；

既要让正常用户能抢到，又绝对不能**超卖（库存负数）**，还要防黄牛、防刷、不压垮数据库

## 秒杀系统要解决的痛点

**流量爆炸**：瞬间 QPS 拉满，直接冲垮 DB / 接口

**超卖风险**：多线程同时扣库存，没锁就会卖爆

**恶意刷单**：黄牛脚本抢货，普通用户抢不到

## 如何设计一个秒杀系统

设计秒杀系统，我的核心思路是**先把数据读走，再异步处理写**。

**先把数据读走： 先读走的是****Redis 预热的秒杀剩余库存与可抢状态，用来前置快速判定抢购资格、拦截无效流量；**

**再异步处理写： 真正扣库存、落订单的写操作，再通过 MQ 异步兜底执行。**

**第一步**，前端页面静态化并放到CDN，降低服务器压力。

- **这是第一层防护**。秒杀**一秒之内**几十万人刷页面。如果把页面放在我们自己的服务器端上，瞬间的页面流量都有可能把服务器冲垮。
- 把页面搞成纯静态的 HTML CSS JS，将静态资源直接放到 CDN 上。用户打开页面时，从最近的 CDN 上拿页面。
- 把 90% 的页面流量，直接挡在 CDN，根本进不了后端，后端只需要扛 **下单抢库存 **的核心接口，不用扛刷页面的洪水
- 点击后立即禁用按钮并显示“处理中…”，同时设置3-5秒的定时器或根据接口返回结果恢复状态。防止用户重复提交请求，减轻服务器压力。

**第二步**，Nginx层做IP限流和用户校验。

- IP 限流是指：在请求还没进到业务代码前，先把频繁刷、恶意 IP 挡在大门外，砍掉垃圾流量、减轻后端压力。（比如单个 IP 1 秒最多放 5 个请求，如果 1 秒请求数量超过 5 个请求，说明是脚本刷单）
- 用户校验是指：先验身份，拦截匿名用户，看看是不是被封的黑号，把无效用户挡在业务入口外，减轻后端压力。

**第三步**，核心逻辑放在应用层：活动开始前，把库存预热到Redis中。
**第四步**，用户请求到达时，先用**Redis Lua脚本原子扣减库存**，成功后立即发送消息到MQ。
**第五步**，后端服务从MQ中异步拉取消息，再写入数据库完成订单创建。

同时，为了防止超卖，我在Redis和数据库两个层面都做了原子性保证（**Redis 中使用 lua 脚本保证原子性，数据库层面用单条 UPDATE 语句自动加行锁的机制来保证原子性**）。为了防止机器刷单，我们会引入验证码（**IP 高频的可以弹出验证码**）和用户行为风控。通过这种方式，理论上可以支撑百万级的QPS。

**数据库层面的原子性怎么理解？**

**错误写法：**

```java
// 1. 先查库存
int stock = select stock from goods where id=?;
if(stock > 0) {
    // 2. 再扣库存
    update goods set stock=stock-1 where id=?
}
```

**正确写法：**

```java
// 只发这一句 SQL
int rows = update(
    "UPDATE seckill_goods SET stock=stock-1 WHERE id=? AND stock > 0"
);

// 影响行数 > 0 代表扣成功，否则扣失败
if(rows > 0) {
    // 扣库存成功 → 生成订单
} else {
    // 库存不足
}
```

# 如何实现接口的限流和降级？

## 限流

**在网关层****：我们通常使用令牌桶算法**以及**漏桶算法 ****配合Nginx网关层做IP限流**：

**令牌桶算法：以固定速率往桶里放令牌，每个请求必须拿到一个令牌才能通过，桶里有令牌积压时允许突发流量。（固定速率放令牌**、**允许突发）**

**漏桶****算法：请求先进入桶里，无论进来多快，都以固定速率从桶底漏出去处理，桶满了就丢弃。固定速率流出**、**强制平滑**（进来再猛，出去也是匀速）

**在应用层**也可以做限流，可以使用谷歌提供的一个工具：**Guava RateLimiter**

**Guava RateLimiter** 是 Google 提供的 Java 限流工具，**基于令牌桶算法，在单机内存中限制某个代码块的执行频率**

就是在一台机器的 JVM 内部，控制某个方法一秒最多被调用多少次，超过就阻塞或拒绝。

## 降级

降级是当系统**压力过大、依赖服务不可用或发生异常**时，**主动关闭非核心功能**或**返回兜底数据**，保证**核心业务可用**。

降级是一种**有损服务**，目的是**避免整体系统崩溃**。

**降级方面，通过 Sentinel 配置熔断降级规则，比如慢调用比例超过 50% 时触发熔断，直接走 fallback 返回缓存数据或默认提示。非核心功能如评论、推荐在大促时手动降级关闭，保证下单等核心链路稳定。**

# 如何处理热点数据问题？

**热点数据问题的核心是单个Key被海量请求同时访问，打爆Redis单节点或数据库。**

**为什么会打爆？ Redis 单节点处理能力有物理上限（比如网卡带宽、比如只能单核 CPU 处理、比如连接数有上限），而海量请求全部打向同一个节点，超过上限就会被打爆。**

**解决方案分三步：**

- **第一步，发现热点**：通过监控工具（如Redis的`<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">--hotkeys</font>`命令）提前识别热点Key。这个命令会**打印出访问频率最高的那些 Key 的名字以及它们所在的数据库编号**
- **第二步，多级缓存**：在Redis之前增加**本地缓存**（Caffeine），将热点Key加载到应用服务器内存中，90%的请求直接由本地缓存返回，不再经过Redis。但它存在数据不一致的风险，解决办法是 **设置短过期时间（如10秒），允许 10 秒内数据不一致，让不一致的时长可控；强一致性数据（如库存）不走本地缓存。**
- **第三步，拆分打散**：如果本地缓存还不够，将**热点Key**拆分成多个**子Key**。比如原本一个商品库存Key `<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">stock:1001</font>`，拆成10份：`<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">stock:1001:1</font>`到`<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">stock:1001:10</font>`，每份库存100件。请求通过**随机哈希分散**到这10个Key上，把单节点压力分摊到多个Redis节点。

**一句话总结：本地缓存 挡 第一波，Key拆分 挡 第二波，层层削峰，把热点打散成多点。**

# AQS原理是什么？

可以把AQS（AbstractQueuedSynchronizer）想象成一个“**排队管理器**”。它解决的是多线程争抢同一个资源时，谁用、谁等、用完叫谁的问题。

我们拿“**去银行办业务**”来打个比方：

- **资源**：银行只有1个柜台窗口（相当于锁，一次只能一个人办业务）。
- **线程**：来办业务的顾客。

## AQS 的核心：两样东西

AQS内部主要维护了两样数据：**AQS 可以看做是大堂经理**

- **一个 2 量（状态标识）**：相当于“窗口指示灯”。**0** 表示窗口空闲，**1** 表示窗口有人。
- **一个 **`CLH`** 队列（等待队列：**CLH 是一种**排队算法的名称**，取自三位发明者 **Craig、Landin、Hagersten** 的名字首字母，在 AQS 的语境下，**CLH 队列**指的是 AQS 内部用来管理等待线程的**双向链表结构****）**：相当于银行里的**排队等候区**。抢不到资源的顾客，不会在外面乱逛，而是会在这个队列里**排队**，并**休眠**（阻塞），节省CPU资源。

## 它是怎么运作的？

我们来看第一个顾客（线程A）和第二个顾客（线程B）分别会遇到什么：

- **线程A 来了（获取锁）**：
它看一眼 `state`（窗口灯）。如果是0（空闲），它立马把 `state` 改成1（亮起红灯，表示占用），然后直接跑到窗口办业务。**这个过程不需要排队。**
- **线程B 来了（获取锁失败）**：
它来时看到 `state` 是1（窗口有人）。AQS会告诉它：“你没抢到，先去等候区坐着（进入CLH队列），**别在这浪费CPU**。”
- **线程A 办完了（释放锁）**：
A 办完业务出来，把 `state` 改回0。这时 AQS 会去**队列头部**看一眼：如果有排队的，AQS会把队首的线程B**唤醒**，说：“轮到你了”。
- **线程B 被唤醒（再次获取锁）**：
B 被唤醒后，会再次尝试把 `state` 从0改成1。如果成功，它就从队列里移除，去窗口办业务。

## 两种模式（独占 / 共享）

AQS提供了两种排队方式，对应不同的场景：

- **独占模式**：**“一个坑只能一个人”**。就像柜台一次只服务一个人。`ReentrantLock` 就是这种，只要线程A没出来，线程B就得死死等着。
- **共享模式**：**“多个坑位同时用”**。比如一个窗口有3台自助取款机，如果还有空机子，后面的顾客不用等，可以直接上。`CountDownLatch`（门闩）和 `Semaphore`（信号量）就是这种。

## 为什么它叫“抽象队列同步器”？

把它拆开看：

- **同步器**：它解决线程同步问题。
- **队列**：它用“排队”来解决争抢，让没抢到的线程乖乖等着，避免了疯狂争抢导致的CPU崩溃。
- **抽象**：它只把“怎么排队”、“怎么休眠/唤醒”这些麻烦的底层逻辑写好了。至于“到底算不算抢到资源”（即修改 `state` 的规则），它留给了开发者去定义。

## 总结

AQS本质上是一个**基于双向队列的线程调度框架**。

它做了**99%的脏活累活**（维护队列、阻塞、唤醒线程），只留了一个核心问题给开发者：**“什么算拿到锁？”** 开发者只需要重写 `tryAcquire` 方法，判断一下 `state` 的值，剩下的排队逻辑全交给AQS搞定。

Java里 `ReentrantLock`、`Semaphore`、`CountDownLatch` 这些工具，底层都是通过AQS这个“排队管理器”来实现的。

- `**<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">ReentrantLock</font>**`：**独占锁**，一次只允许一个线程进入，但同一个线程可以重复进入（可重入），适合解决**互斥**问题。
- `**<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">Semaphore</font>**`：**共享锁**，允许指定数量的多个线程同时进入，适合做**限流**（比如最多5个并发）。
- `**<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">CountDownLatch</font>**`：**门闩**，让一个或多个线程等待其他N个线程都"完成"之后才继续执行，适合做**等待多个任务全部就绪**的场景。
